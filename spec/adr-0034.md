# ADR 0034: opt-in int8 weights (row-wise scales) on the HIP/CUDA bridge

Status: accepted as an opt-in, lossy option (`--int8-weights`). Measured on
GeForce RTX 4060, WSL2, CUDA 13.3; see
spec/measurements/cuda-rtx4060-int8.json. Not built or run on the RX 7900
XTX yet.

## Context

Decode reads about 1.5 GB of BF16 weights per token. On every GPU here it
is bound by memory bandwidth: on the RTX 4060 the matrix-vector products
are about 93% of a 7.2 ms step (ADR 0033). Fewer weight bytes is the
remaining lever, and spec/roadmap.md section 5 lists quantization for it.

Every option so far keeps the values. ADR 0006 allows only lossless
formats by default and asks lossy ones for their own ADR and tolerances.
The roadmap also asks quantization to be something one can observe: what
changes, and by how much. A CPU check alone would just report it as an
error.

## Decision

**Format (`WeightFormat::Int8`, `--int8-weights`, opt-in).**

- Every projection matrix is stored as int8 with one FP32 scale per row.
  This includes the vocabulary projection.
  - `scale = max |w| / 127`, and `q = round-half-even(w / scale)`, clamped
    to ±127. So `|w − scale·q| ≤ scale / 2`.
  - An all-zero row has scale 0.
  - `quantize_int8_rows` in src/device.rs implements this.
- Activations, state, products and sums stay FP32. A row computes
  `y = scale · Σ_j q_j x_j`, applying the scale once after the reduction.
- The embedding lookup keeps the BF16 matrix. The vocabulary projection
  uses its own int8 copy (`DeviceModel::lm_head`), so the tied matrix is
  stored twice: 1.26 GB in all against 1.50 GB. A decode step reads about
  0.75 GB of int8 weights instead of 1.5 GB of BF16.
- `*-verify` and `*-speculative` keep BF16 weights. They do not take
  `--int8-weights`.

**Bridge (no ABI bump; optional symbols, as in #19).**

- `qr_gemm_i8(ctx, y, packed, x, rows, cols, batch)` has `qr_gemm_bf16`'s
  arguments. `packed` is one buffer: `rows` FP32 scales, then the
  row-major int8 values.
- `qr_gemm_i8_group`, `qr_gemm_i8_glu` and `qr_gemm_i8_add_norm` are the
  int8 versions of the BF16 group, GLU and GEMV + Add + RmsNorm calls.
- Kernels (kernels.h, shared by HIP and CUDA):
  - `gemv_i8_lane` is one wave per row. Each lane makes 16-byte loads
    (16 values), with two in flight. `gemv_i8`, `gemv_i8_group`,
    `gemv_i8_glu` and `gemv_i8_add_norm` all build on it. The add-norm
    tail repeats `gemv_bf16_add_norm`'s ticket protocol and expressions.
    The BF16 kernels are untouched.
  - `gemm_i8_tiled` serves prefill (16 tokens and more). It is
    `gemm_bf16_tiled` with 8-byte int8 loads.
  - `gemv_i8_block` handles shapes without 16-byte rows (`cols % 16`,
    `rows % 4`).
- The CPU test bridge computes the same expressions in index order. The
  Metal bridge has no `qr_gemm_i8`, and `--int8-weights` is refused there
  by name.

**How it is judged.** A CPU check is expected to fail:
`cuda-check --ids 16,10,16,28 --int8-weights` stops at layer 0's
`post_norm` with 0.024 against the 3e-3 tolerance. Instead, the ignored
test `device_real_int8_quality` (tests/device_gpu.rs) runs the BF16 and
the int8 engine side by side:

- It takes README.md with a 32-token prompt, then 512 positions fed token
  by token.
- At every position it compares the top-1 token, the rank of the BF16
  top-1 under int8, KL(BF16 ‖ int8), the largest logit difference and the
  perplexity of the actual text.
- At the first position it also compares the residual after every layer.
- It prints the report and asserts only loose bounds: top-1 agreement
  ≥ 0.9 and perplexity ratio < 1.1.

## Results (RTX 4060)

**What changes** (512 positions):

| measure | value |
|---|---|
| top-1 token agreement | 96.3% |
| rank of the BF16 top-1 under int8 | median 0, max 1 (always 1st or 2nd) |
| KL(BF16 ‖ int8) | mean 0.0024, median 0.0019, max 0.060 nats |
| largest logit difference | 1.11 |
| perplexity of the README text | 25.41 → 25.57 (+0.6%) |
| residual after each layer, relative L2 | 2.0–2.6%, flat over the 24 layers |

The quantization error does not build up through the layers. Each layer's
residual differs by about the same 2%.

Greedy generation, 64 tokens, against BF16:
- identical for the 4-token prompt and the 9,872-token prompt;
- the 1,267-token prompt diverges at token 27, after which the wording
  differs.

**Speed.** `cuda-infer`, 64 new tokens, 3 runs, BF16 and int8 alternated:

| input | BF16 decode | int8 decode | |
|---|---|---|---|
| 4 tokens | 137 token/s | 239 | 1.75x |
| 1,267 | 135 | 231 | 1.71x |
| 9,872 | 119 | 190 | 1.60x |

Prefill is compute-bound and unchanged (9,872 tokens: 4.9 s).

Decode step with Nsight Systems, 4-token prompt:

| | step | kernels | kernel time | gaps |
|---|---|---|---|---|
| BF16 | 7.20 ms | 137 | | |
| int8, first version (no int8 group/GLU/add-norm) | 5.76 ms | 300 | 3.81 ms | 1.73 ms |
| int8 | 4.20 ms | 137 | 3.80 ms | 0.28 ms |

The first version used the fused calls only for BF16. That doubled the
launches, and on WSL2 the host (about 6 µs per launch) could not keep the
GPU fed. The int8 fused calls restore the BF16 launch count.

The int8 kernels read 200–250 GB/s of weights: the vocabulary projection
takes 1.02 ms for 254 MB. The 1.6–1.75x falls short of 2x for two
reasons. The non-projection kernels are unchanged, and the step's fixed
host and readback costs stay.

**Tests.** All pass.

- CI (CPU test bridge):
  - `int8_quantization_rows`: error bound, zero row, ±127;
  - `cpu_bridge_int8_projection`: bitwise against an index-order
    reference, odd sizes and padding, and an int8 fixture model;
  - `cpu_bridge_int8_fusions`.
- GPU (ignored):
  - `gpu_bridge_int8_projection`: decode, 3 and 9 tokens (two token
    blocks), tiled 20 and 40 tokens, and an unaligned 5×37, against the
    CPU test bridge;
  - `gpu_bridge_int8_fusions`: group, GLU and add-norm are bitwise equal
    to the separate calls;
  - `device_real_int8_quality`.
- The BF16 `device_gpu` tests are unchanged.

## Consequences

- `--int8-weights` exists for `*-check`, `*-infer` and `*-chat` on the
  HIP and CUDA bridges. It changes results, so it is never the default.
  Reports state `"weights": {"format": "int8", "int8_matrices": 187}`.
- A kernel change to the int8 path must keep the fused calls equal to the
  separate ones (`check_int8_fusions`).
- Not done:
  - 4-bit or group-wise scales: more bytes saved, larger changes; a
    separate decision.
  - int8 on Metal.
  - An int8 MTP head.
  - A ROCm measurement.
