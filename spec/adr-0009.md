# ADR 0009: parallel RMSNorm; FFN gate/up fusion rejected

Status: experimental; passed on Apple M5 (macOS 27.3), Metal engine. ABI and
the HIP/CPU bridge are unchanged. HIP got its own version in ADR 0013. See spec/measurements/metal-m5-norm.json.
CPU reference remains the oracle and ADR 0004 tolerances are unchanged.

## Context

To decide which kernels to fuse, decode was profiled with a scratch build of
the bridge that puts every dispatch in its own command buffer and sums
GPUEndTime - GPUStartTime per kernel (64 decode tokens, short prompt). That
showed `rms_norm` at 22% of GPU time, about 78 us per call: the kernel ran
one thread per group, so the hidden-size norm (1 group x 1024) was a single
GPU thread summing serially. 67 norms run per token.

## Decision 1: one threadgroup per RMSNorm group (Metal only)

Op 1 is dispatched as `rms_norm_group`: one threadgroup (<= 256 threads) per
group, sum of squares by SIMD + threadgroup reduction. Same op, slots and
ABI (v3); the HIP/CPU body is unchanged. The reordered sum is covered by ADR
0004 tolerances.

## Decision 2: no fused gate/up/SiLU kernel

The same profile put the two 3584x1024 gate/up GEMVs at 23% (about 64 GB/s).
A fused kernel was built and tested (gate and up stacked into one matrix,
one SIMD group reading both rows and writing silu(g)*u, bit-identical to the
unfused path, ABI v4 with HIP/CPU versions). Repeated end-to-end runs showed
no gain: fused 66.4/66.3/66.4 tok/s, one stacked GEMV + SiLU
66.4/66.2/66.4, separate GEMVs 66.0. Per-command-buffer profiling inflates
small kernels that overlap in the normal single-encoder stream, so it ranked
this fusion too high. Not worth an ABI bump and three bridge copies in a
learning codebase; reverted.

Timing per decode token after Decision 1 (single command buffer): CPU
encoding 0.125 ms, GPU 14.6 ms, commit-to-completion 15.2 ms. Decode is GPU
bound, not sync bound, so removing syncs would gain at most about 0.5 ms.
1.5 GB of weights in 14.6 ms is about 103 GB/s effective; the vocabulary
GEMV alone reaches about 137 GB/s.

## Consequences

M5, BF16, chunk 128, 64 new tokens, single runs: decode 50.1 -> 65.9 tok/s at
454 tokens, 47.9 -> 62.3 at 2644, 40.1 -> 49.7 at 10141; prefill slightly
faster. All 64 generated tokens identical to the ADR 0008 runs. Real check
max error 1.74e-4, 2048-token long check 3.21e-4.

A follow-up GEMV benchmark (repo `gemv_bf16`, bridge dispatch shape, many
dispatches in one command buffer, up to 64 matrix copies cycled to defeat
caches) found every model shape at 123-138 GB/s except 512x1024 (101) and
16x1024 (9, launch bound), against a raw read rate of 132 GB/s. The 1024-
column GEMVs are therefore not slow; the per-kernel profile was misleading
there too. GEMVs total 11.5 ms of the 14.6 ms GPU time per token, so BF16
decode is bounded near 80 tok/s; the other ~3 ms are the ~400 non-GEMV
dispatches (DeltaNet rule, attention, small ops). Going past the bound needs
fewer weight bytes (lossy formats: a separate ADR). Any further fusion must
be justified by end-to-end runs, not by the per-kernel profile.
