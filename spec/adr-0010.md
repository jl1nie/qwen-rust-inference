# ADR 0010: weight edits and traces on the device engines

Status: experimental; passed on Apple M5 (macOS 27.3), Metal engine, and on
the CPU test bridge. ROCm shares the code but is not GPU-verified. ABI and
kernels are unchanged (v3). CPU reference remains the oracle.

## Context

The CPU engine supports edit manifests (`src/edit.rs`: unit zeroing and
down-column direction removal as activation/output overlays) and NDJSON
traces (`src/trace.rs`). The device engines had neither. Short prompts are
fine on the CPU, but observing position 8000 or comparing long edited
generations is only practical on the GPU (CPU prefill: ~2.5 min at 2048
tokens).

## Decision 1: edits are the CPU overlay applied to read-back products

`DeviceRun::set_edit(model, manifest)` runs the CPU validation
(`EditManifest::validate`: revision, layer, exact tensor name, columns,
direction) and keeps host FP32 copies of the down matrices of the edited
layers only. In `forward`, for an edited layer only: read back the FFN
product rows, call the unchanged `EditManifest::apply` per row, write the
product back, run the down projection, then add the direction correction
with the existing `Add` op (the dead `mixed` buffer is the scratch). Device
weights are never modified; `reset` keeps the edit, `set_edit(None)`
removes it. No kernel or ABI change, so the math is literally the CPU code.
Rejected: GPU kernels for the overlay (ABI bump, three bridge copies) for a
cost that is one sync per edited layer per forward pass.

## Decision 2: traces use the CPU format for one position

`<engine>-infer --trace PATH --trace-position N` writes the CPU NDJSON
records through `Trace::record` with the CPU operation names, tagged
`"engine":"metal"|"rocm"` (an optional field; CPU traces are unchanged).
The prompt up to N is prefilled in chunks, position N runs alone with
captures, the rest continues normally; N may also be a generated position.
Exactly one position is required, so a long run cannot dump everything.
Records per layer: input, input_norm, mixer, after_mixer, post_norm,
ffn.product, ffn.intervened_product, ffn.output, layer; then final_norm and
logits. `embedding`/`input` of layer 0 is the host row (BF16 widening is
exact). Mixer internals (Q/K/V, scores, probabilities, DeltaNet internals)
and ffn.gate/up/silu stay CPU-only: the matrix-unit and split attention
kernels never materialize probabilities. The same --trace-layer,
--trace-max-bytes and --trace-full rules as the CPU apply.

## Consequences

Real weights, ids 16,10,16,28: all 11 device records of layer 3 at position
2 match the CPU trace (max abs error <= 3.1e-5, same top logit). With
`examples/zero-unit.json`, layer 0 at position 3 matches too and unit 3 of
ffn.intervened_product is -0 on both engines. Both example manifests give
the CPU's last-position logit shift (5.30 and 0.2642 L2) and the same 12
generated tokens; edited decode runs at ~65 tok/s vs ~66 unedited.
`--compare-edit` reports the unedited baseline generation and repetition
metrics. A CPU-bridge unit test checks decode, chunked prefill, reset and
removal against the CPU engine, and fails if the correction add is dropped.
