# ADR 0015: faster Metal prefill (DeltaNet registers, block attention, 64x64 GEMM)

Status: accepted; passed on Apple M5 (macOS 27.3). See
spec/measurements/metal-m5-prefill.json. CPU reference remains the oracle.
ABI v3 is unchanged; the HIP bridge is unaffected (the KV padding is shared
Rust code and harmless there).

## Context

Against MLX on the same prompts, prefill was 7-11x slower
(spec/measurements/mlx-comparison-m5.json). A per-dispatch profile at 2644 /
10141 prompt tokens split prefill time as follows:
- GEMMs: 66 % / 53 %.
- DeltaNet rule: 21 % / 17 %.
- Prefill attention: 9 % / 27 %.

## Decision

Each step was checked against the previous build: generated IDs, the exact
prefill top-5 logits, the GPU tests and the 2048-token long check.

1. `delta_rule_reg<KD>` (key_dim 64/128). Each thread loads its state
   column into registers once per dispatch, runs the chunk's tokens on it and
   stores it once. Before, it read and wrote the column in device memory
   twice per token. The operations and their order are the same:
   **bit-identical**. The delta_rule time fell from 960 to 256 ms at 2644
   tokens.
2. `attention_mma`, block version:
   - Each simdgroup (one head) runs on its own.
   - K/V 8x8 tiles are loaded straight from device memory; the G heads of a
     KV head share them through the cache. The threadgroup K/V staging and
     its barriers are gone.
   - Positions are taken 32 at a time (4 score tiles), so the accumulator
     correction happens once per 32 positions instead of per 8.
   - The softmax uses all 32 lanes: 4 per row, combined with quad shuffles.
   - KV buffers are padded to whole 32-position blocks (`kv_rows`). Padded
     rows are always masked.

   The summation order changes, within the ADR 0004 tolerance. With
   block 32 the generated IDs did not change on the test prompts.
   Rejected:
   - Holding Q in registers: it spills at head_dim 256 (10141-token prefill
     16.4 s, slower than before).
   - Blocks of 16 or 64: slower, or a greedy token changed.
3. `gemm_tiled`:
   - Output tile 64x64 (was 32x32), with 4 SIMD groups of 32x32 each. Each
     has 4x4 accumulators: 16 multiply-adds per 8 tile loads.
   - X and W are staged with float4 / 4-wide BF16 loads when rows are
     4-aligned.
   - The K loop is unchanged (blocks of 32, 8 columns at a time in order), so
     every output is accumulated in the same order: **bit-identical**.
   - Full unrolling of the 4x4 loops is required; without it the arrays
     spill and the kernel is 4x slower.

   Rejected: a K block of 64 (lower occupancy) and a 64x128 tile with 8
   SIMD groups (slightly slower).

## Consequences

M5, BF16 weights, chunk 128, 64 new tokens:

| prompt | prefill before | prefill after | speedup | decode after |
|---|---|---|---|---|
| 454 | 743 tok/s (0.61 s) | 1405 tok/s (0.32 s) | 1.9x | 67.4 tok/s |
| 2644 | 727 tok/s (3.64 s) | 1567 tok/s (1.69 s) | 2.2x | 63.5 tok/s |
| 10141 | 556 tok/s (18.25 s) | 1292 tok/s (7.85 s) | 2.3x | 48.7 tok/s |

Steps 1 and 3 change no value. The 2048-token long check passes with max
error 3.21e-4 (before 3.2e-4); device prefill in that check took 3.48 s ->
1.82 s. Decode is unchanged or slightly faster.

MLX BF16 is still 3.8-4.8x faster at prefill. The remaining gap is mainly
the GEMMs: about 1.6 TFLOPS here, in FP32 with 8x8 matrices. MLX runs
16-bit matrix arithmetic and gets well above what FP32 can reach. Closing
it needs 16-bit GEMM inputs, which changes values. That would be an opt-in
with its own tolerance, like ADR 0014.

Small follow-ups:
- `gemm_tiled` is templated on the tile. Matrices with at most 16 rows (the
  DeltaNet a/b projections) use 16x64 tiles (4 SIMD groups of 16x16)
  instead of leaving 48 of 64 rows empty. The K order is the same:
  bit-identical. 16x1024 GEMMs went from 105 to 88 ms at 2644 tokens, about
  1 % of prefill. These 756 tiny calls are bound by launch latency, not by
  the empty rows.
- The DeltaNet rule's threadgroup width was swept: 256, 128, 64 and 32 all
  gave the same time (1.705-1.718 s at 2644 tokens). The kernel is bound by
  each thread's token-to-token dependency, not by how threads spread over
  the cores, so the width is unchanged.

Not done: the DeltaNet rule is still sequential in tokens. Chunked
delta-rule algorithms parallelize over tokens but change the arithmetic.
