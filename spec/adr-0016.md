# ADR 0016: Metal prefill GEMMs on Metal 4 tensor ops; opt-in relaxed precision

Status: accepted; passed on Apple M5 (macOS 27.3). See
spec/measurements/metal-m5-tensor-matmul.json. CPU reference remains the
oracle. ABI v3 is unchanged (optional symbol `qr_set_option`); the HIP bridge
rejects the new option names.

## Context

After ADR 0015, Metal prefill was still 3.8-4.8x slower than MLX, mostly in
the GEMMs (~1.6 TFLOPS in FP32 with 8x8 simdgroup matrices). The first idea
was to round GEMM inputs to FP16 inside the same simdgroup kernels. Measured
on M5 this was slower (2644 tokens: 1.93 s vs 1.73 s): half-precision
`simdgroup_matrix` multiplies have no higher throughput there, so only the
conversions were added. Rejected and removed.

MLX's Metal library contains "NAX" GEMM kernels built on
`mpp::tensor_ops::matmul2d` from MetalPerformancePrimitives: the Metal 4
tensor ops, which run on the GPU's matrix hardware (the neural accelerators
of Apple M5). Their supported types include **float x bfloat -> float**, our
exact case, and a `relaxed_precision` flag. A standalone harness (3584x1024,
128 tokens, outside the repository) measured:
- `relaxed_precision = false`: 2.6 TFLOPS, max error 6.25e-6 (FP32 level).
- `relaxed_precision = true`: 6.2-6.4 TFLOPS, max error 1.8e-3.

Our gemm_tiled kernel ran this shape at about 1.46 TFLOPS.

## Decision

- `native/metal/kernels_tensor.metal`:
  - `gemm_tensor_{f32,bf16}` and `..._relaxed`.
  - Y[batch,rows] = X[batch,cols] . W[rows,cols]^T: `tensor_inline` views on
    the existing buffers, W as the transposed right operand, a cooperative
    destination tensor zeroed and then stored.
  - 32 tokens x 64 rows per threadgroup of 4 SIMD groups; 128 x 64 when
    relaxed.
  - Compiled at runtime as a second library with Metal language 4.0, in
    safe math mode.
  - If that fails (macOS < 26, older GPU), the bridge keeps the gemm_tiled
    kernels, bit-identical to ADR 0015. `device_info` reports
    `prefill_gemm=metal4-tensor-ops` or `unavailable`. `QR_METAL_VERBOSE=1`
    prints the compile error.
- **Default:** prefill GEMMs (>= 8 tokens, > 16 rows) use the tensor ops
  with `relaxed_precision = false`. Inputs are not rounded; only the
  summation order differs, as in ADR 0007/0015. The existing tolerances
  apply. `--no-tensor-matmul` (bridge option `matmul_tensor=0`) selects the
  gemm_tiled kernels for A/B checks.
- **Opt-in `--matmul-relaxed`** (bridge option `matmul_relaxed=1`) lets the
  hardware trade accuracy for speed. It changes results, so it is never the
  default. It is an error when tensor ops are unavailable.
  - Reports record `"matmul": "relaxed_prefill"`.
  - Tolerance `MATMUL_RELAXED_TOLERANCE = (0.12, 0.12)`, about 2.3x the
    worst measured error (the same rule as ADR 0014).
  - The greedy token must still match at every long-check boundary.
- Decode (GEMV), attention, DeltaNet and the KV cache are unaffected.

## Consequences

M5, BF16 weights, chunk 128, 64 new tokens:

| prompt | gemm_tiled (ADR 0015) | tensor ops (default) | relaxed (opt-in) |
|---|---|---|---|
| 454 | 1384 tok/s | 1677 tok/s | 2565 tok/s |
| 2644 | 1.73 s | 1.48 s | 0.93 s |
| 10141 | 8.04 s | 7.12 s | 4.97 s |

- Generated tokens are identical in all three modes on all three prompts.
- Decode is unchanged.
- 2048-token long check max error: 3.21e-4 with gemm_tiled, 3.21e-4 with
  tensor ops, 5.06e-2 relaxed (cosine >= 0.9999957).

Against MLX BF16 (5,300-6,200 tok/s) the default is now 3.2-4.3x slower and
relaxed 2.1-2.9x. The remaining part is prefill attention and the DeltaNet
rule, still FP32 simdgroup or scalar code.

`device_real_tensor_matmul` (macOS GPU test) checks three things: tensor vs
gemm_tiled within the FP32 tolerance; relaxed vs the FP32 token-by-token run
within its tolerance, with the same argmax; and a relaxed long check.
