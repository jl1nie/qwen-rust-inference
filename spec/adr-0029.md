# ADR 0029: state snapshots and decode attention for 2-4 rows on ROCm (port of ADR 0026)

Status: accepted. See spec/measurements/rocm-7900xtx-snapshots.json, ADR
0023, 0024 and 0026-0028.

## Context

ADR 0026 added a verify pass that can be rolled back (`verify_rollback`,
`accept`) on Metal. The bridge stores per-token DeltaNet snapshots
(`qr_snapshots`), and the decode attention runs once per row for 2-4 query
rows. The HIP bridge had neither. On ROCm, `new_run_rollback`,
`rocm-speculative` and the rollback parts of `device_real_rollback` and
`device_real_speculative` therefore stopped with "bridge has no state
snapshots". A plain verify needed a host checkpoint of about 19 MB before
every pass, 6.3-9.5 ms or about 2 decode steps (ADR 0023).

## Decision

- **`qr_snapshots`.** native/rocm/bridge.cpp exports it in both builds,
  the HIP bridge and the CPU test bridge. ConvSilu with n3 = S > 0 and
  DeltaRule / DeltaRuleGated with n6 = S > 0 store the state after token
  r < S into copy r. The copies sit right after the live state in the same
  buffer, with Metal's layout.
  - ConvSilu: `conv_silu_channel<SNAP>` (reference.h), run by a new
    `conv_silu_snapshots` kernel. Without snapshots, ConvSilu stays on
    `reference_kernel` as before.
  - DeltaRule: `delta_rule_column<..., SNAP>` and `delta_rule_registers`
    (kernels.h). The snapshot code is a separate template instance. The
    fused decode kernels (`delta_mixer_split`, `delta_mixer_block`) and the
    plain launches compile without it, so their code size does not change
    (ADR 0019: on WSL2, kernel size costs time per dispatch). Rust already
    skips the fused mixer in a snapshot pass.
  - The CPU test bridge stores snapshots in its scalar bodies. The kd > 128
    reference fallback on HIP refuses snapshots.
- **Decode attention for 2-4 query rows.** In `attention()`, when
  `--attention-f16` is off, the bridge runs the decode attention
  (`attention_tiled` with splits, then `attention_combine`) once per row r,
  over n3 + r positions. Output, query and gate are offset by r rows; the
  score scratch is reused, because one stream runs the launches in order.
  Each row is then the decode step of that position, bitwise. This is
  needed for rollback: `accept` must leave exactly the state of sequential
  decode. Five or more rows keep the chunk attention.
- **Test.** New `cpu_bridge_rollback_matches_sequential_decode`
  (src/device/tests.rs). It runs a 4-row `verify_rollback` on the tiny
  fixture, then `accept(1..=4)`. The state and the next step must equal
  sequential decode bitwise, and a run without snapshot room must refuse.
  It runs in CI.

## Consequences

**Correctness**

- GPU tests: all 6 pass. `device_real_rollback` and
  `device_real_speculative` now run to the end on ROCm.
  - `device_real_rollback`: after `accept(keep)` for keep 1-4, the state and
    the next step are bitwise equal to sequential decode.
  - `device_real_speculative`: the generated IDs equal plain greedy.
- 2-4 verify rows are now bitwise equal to decode (`max_abs_logit_diff` 0).
  Before, they differed by up to 1e-5.
- Prefill chunks of 2-4 tokens, such as the end of a prompt, also take the
  decode attention. Their values change by summation order: up to 5.7e-6 in
  the prefill top-5 with chunks of 2, 3, 4 and 7 on a 331-token prompt. The
  generated tokens are unchanged.
- Chunk-128 prefill and decode are bitwise unchanged at five prompt lengths.
  The `--ids` check, the tests and the 2048-token long check (2.63e-4) give
  the same results.

**Verify pass.** RX 7900 XTX, median of 15 runs, ms (before = ADR 0024's
ROCm section):

| context | decode | 2 rows | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 454 | 3.57 | 5.05 (5.43) | 5.40 (5.49) | 5.51 (5.87) | 5.95 (6.16) |
| 2644 | 4.19 | 5.58 (7.84) | 5.73 (7.14) | 6.00 (7.42) | 7.76 (7.54) |
| 8192 | 3.94 | 5.46 (12.23) | 5.89 (11.53) | 6.36 (12.67) | 12.13 (12.13) |

- The long-context step from 1 to 2 rows is gone: 2 rows at 8192 tokens
  take 5.5 ms instead of 12.2. At 8192 tokens 2-4 rows cost about 1.4-1.6
  decode steps, as at a short context. Unlike Metal, extra rows do not grow
  with the context here.
- With snapshots stored, a pass costs about the same as without them, and
  no host checkpoint is needed.
- Decode is unchanged (1500 and 10000 bytes, 3 runs each, against main's
  bridge).

**End-to-end greedy speculative decoding.** `rocm-speculative`, 8 prompts,
128 new tokens, draft on the device:

| draft vocabulary | k = 1 | 2 | 3 |
|---|---|---|---|
| 4,096 | 0.93 | 0.95 | 0.88 |
| 8,192 | 0.94 | 0.97 | 0.90 |
| 16,384 | 0.97 | 0.99 | 0.89 |
| 32,768 | 0.94 | 0.95 | 0.87 |

- The generated IDs equal plain greedy in every run. Acceptance and tokens
  per pass (1.6 / 1.9 / 2.0) match Metal's (ADR 0028), since the draft and
  the verified tokens are the same.
- It does not pay off on ROCm yet. Plain decode takes about 3.2 ms per
  token. A pass with k = 2 takes 6.2 ms and yields 1.93 tokens, mostly
  because a 3-row verify costs about 1.5 decode steps. On Metal the same
  pass costs about 1.06.
- ADR 0024's ROCm section splits the 1-to-2-row step:
  - On the GPU, about 0.8 ms: mostly the separate Add + RmsNorm dispatches
    (decode fuses them into the GEMV's last block).
  - On the host, the rest: more dispatches and the logits readback.
    This change adds 2 dispatches per row per attention layer.

Next on ROCm, for speculative decoding:
1. a GEMV + Add + RmsNorm tail for 2-8 rows (`qr_gemm_bf16_add_norm` with a
   token count);
2. fewer dispatches in a verify pass, for example one decode attention
   launch for all rows instead of one per row, keeping each row's summation
   order;
3. the draft's own cost on the device (MTP head and subset projection;
   ADR 0028 profiles it on Metal).
