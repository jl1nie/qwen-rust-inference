# ADR 0026: decode attention for a few query rows; rollback with per-token DeltaNet snapshots (Metal)

Status: accepted. See spec/measurements/metal-m5-verify-rollback.json,
ADR 0023-0025 and spec/roadmap.md item 3.

## Context

After ADR 0024 a verify pass of 2-7 tokens cost about one decode step at a
454-token context, but a constant step remained at long contexts: +3 ms at
2644 tokens and +7.7 ms at 8192 (1.49 decode steps for 2 rows). With 2 or
more query rows the attention took the prefill path (`attention_tensor`),
not the split decode attention (`attention_split_grp`, ADR 0017). The prefill
path also sums in a different order, so a verify pass matched sequential
decode only up to 4.4e-5 in the logits.

A rejected draft also has to be undone. Attention KV only needs its length
reset, but a DeltaNet state has absorbed every token. ADR 0023 measured a
full checkpoint (1.7 ms) before each pass and a restore (1.4 ms) on
rejection, about 0.1-0.2 decode steps per pass.

## Decision

- Attention (bridge.mm, `qr_run`): with 2-4 query rows and the level-2
  decode kernel available, the bridge runs `attention_split_grp` once per
  row r over its own n3 + r positions (Q, output and scratch offset by row).
  Each row is then exactly the decode step at that position. 5 or more rows
  keep the prefill attention.
- Snapshots (`qr_snapshots`, optional bridge symbol): ConvSilu (n3) and the
  DeltaNet rule kernels at levels 1-2 (n6) can store the state after each
  token r < S into copy r, placed right after the live state in the same
  buffer. The fused single-token ops (ADR 0021) are skipped in such a pass.
- `Device::new_run_rollback(capacity, snapshots)` allocates 1 + snapshots
  copies of every DeltaNet state (~19 MiB each). `DeviceRun::verify_rollback(ids)`
  is a verify pass that stores `ids.len() - 1` snapshots; `accept(rows)`
  keeps the first `rows` tokens: the KV length is cut and snapshot
  `rows - 1` is copied into the live state, one device copy per DeltaNet
  layer. Accepting all rows needs no copy.
- `metal-verify` also times `verify_rollback` (`verify_rollback_ms`) when the
  bridge has snapshots; otherwise it falls back to `new_run`.
- ROCm's bridge has no `qr_snapshots` yet, so `new_run_rollback` fails there
  and its attention is unchanged. `rocm-verify` then uses `new_run` and
  reports no rollback time. Rollback counts as available only when
  `new_run_rollback` succeeded. (The first version probed with a 1-row
  `verify_rollback`, which needs no snapshot, so it succeeded on ROCm and
  the 2-row timing failed; issue #36.)

## Consequences

M5, default kernels, median of 15 runs, as a ratio to one decode step:
verify / verify_rollback (before = ADR 0024).

| context | decode | 2 rows | 3 | 4 | 5 | 7 | 8 |
|---|---|---|---|---|---|---|---|
| 454 | 14.02 ms | 1.03 / 1.03 (1.05) | 1.06 / 1.06 (1.07) | 1.05 / 1.08 (1.06) | 1.06 / 1.09 (1.04) | 1.10 / 1.17 (1.10) | 1.68 / 1.77 |
| 2644 | 14.47 ms | 1.05 / 1.04 (1.21) | 1.10 / 1.11 (1.21) | 1.12 / 1.17 (1.19) | 1.18 / 1.23 (1.17) | 1.25 / 1.29 (1.22) | 1.79 / 1.88 |
| 8192 | 15.79 ms | 1.12 / 1.11 (1.49) | 1.23 / 1.24 (1.50) | 1.35 / 1.38 (1.47) | 1.47 / 1.51 (1.48) | 1.51 / 1.58 (1.52) | 2.03 / 2.10 |

- 2-4 rows are now bitwise equal to decoding the same tokens one at a time
  (`max_abs_logit_diff` 0, argmax equal in every row). 5 or more rows still
  differ by summation order (up to 1.8e-5).
- The constant step is gone. What is left grows with the row count at long
  contexts: each row reads the KV cache once more (about +1.8 ms per row at
  8192 tokens). One pass over the KV for all rows would remove it, but would
  change the summation order of the decode kernel.
- Storing the snapshots costs 0-0.07 decode steps (more with more rows).
  It replaces the checkpoint before every pass and the restore on
  rejection. `accept`'s copy (~19 MiB) was below the run-to-run noise.
- `device_real_rollback`: after `verify_rollback` and `accept(rows)` for
  every `rows`, the state and the next decode step are bitwise equal to
  decoding the kept tokens one at a time. `device_real`, `device_real_verify`
  and `device_real_kernel_levels` pass; decode and prefill are unchanged.
- A first run at 454 and 2644 tokens showed 1.19-1.20 for 3 rows; repeats
  gave 1.06 and 1.10 (recorded). The machine's noise is about +-0.05.

| 2644 | 1.19 / 1.15 / 1.05 | 1.50 / 1.68 / 1.74 | 1.50 / 1.67 / 1.71 | 1.47 / 1.62 / 1.64 |
| 8192 | 1.14 / 1.07 / 0.96 | 1.42 / 1.52 / 1.49 | 1.41 / 1.51 / 1.47 | 1.39 / 1.47 / 1.42 |

(ADR 0025: 1.61, 1.48 and 1.26 for 8,192 rows and k = 3.) The next step is
the draft itself on the GPU (the MTP head and the subset projection) and the
speculative loop, measured end to end against plain greedy.

## ROCm (issue #36)

Re-checked on the RX 7900 XTX after this change, with the `rocm-verify` fix
above. See spec/measurements/rocm-7900xtx-rollback-check.json.

- **Tests:** `cargo test --features rocm` passes (54 tests), and so do the
  GPU tests. `device_real_rollback` returns early because
  `new_run_rollback` refuses the run.
- **`--ids` check:** max 1.52e-4.
- **`rocm-infer`:** the generated tokens and the bitwise prefill top-5 match
  main before PR #35 at 13 / 331 / 1267 / 2060 / 9872 tokens. Decode stays
  at 290-335 token/s.
- **`rocm-chat`:** two turns, a resumed turn and a CPU resume of the ROCm
  snapshot give the same text and reuse counts as issue #18.
- **`rocm-verify`:** every row count's `logits_sha256` equals that of
  ADR 0024's ROCm section. Without snapshots, verify still needs the host
  checkpoint (6.6-7.6 ms).

ADR 0029 later ported `qr_snapshots` (ConvSilu, DeltaRule) and the 2-4-row
decode attention to ROCm.

After PR #39 (ADR 0027, 0028), which split `forward` and added hidden
capture, `rewind` and `device::speculative`, the same checks gave the same
results with no code change. That covers the GPU tests (6, including
`device_real_speculative`, which checks the captured prefill hidden rows and
then stops at `new_run_rollback`), `--ids`, the generated tokens and prefill
top-5 at five prompt lengths and with chunks of 5 / 7, `rocm-verify` hashes
and the chat turns. `rocm-speculative` stops at once with "bridge has no
state snapshots (qr_snapshots)", with the draft on the device or on the CPU.
