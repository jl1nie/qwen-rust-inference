# ADR 0007: batched attention read for chunked prefill

Status: experimental; passed on Apple M5 (macOS 27.3), Metal engine. The ROCm
body change is CPU-bridge tested only and not GPU-verified. See
spec/measurements/metal-m5-attention.json. CPU reference remains the oracle
and ADR 0004 tolerances are unchanged.

## Context

After ADR 0006 every op of a prefill chunk was dispatched once for all rows
except the attention read, which still ran once per token: 3 passes
(scores, softmax, weighted sum) x T tokens x 6 attention layers, each pass
re-reading the whole K or V history. Prefill slowed from 615 tok/s at 454
tokens to 115 tok/s at 10141 tokens.

## Decision

Op AttentionRead (10) gets slot n5 = T query rows (0 = one, the v2 meaning).
Row r of the chunk sees positions 0..n3+r (causal); query, gate and context
rows are contiguous [T, heads, head_dim]. Rust issues one dispatch per layer.
ABI is bumped to v3 so a v2 library cannot silently ignore n5.

Engines:
- CPU test bridge / HIP: the one-thread-per-head body loops the T rows in
  order, reusing the head's score row; each row is computed exactly as a
  single-token read, so chunking stays bit-identical on the CPU bridge.
- Metal, T = 1 (decode): unchanged 3-pass read.
- Metal, T > 1, head_dim in {64, 128, 256}: `attention_mma`. One threadgroup
  = 8 query rows x G heads sharing one KV head (G = heads/kv). Per block of 8
  positions, K/V rows are staged once in threadgroup memory (zero beyond the
  written KV); each SIMD group computes S = Q K^T as `simdgroup_float8x8`
  tiles, lanes 0..7 apply the causal mask and an online softmax (running max
  and denominator) for their row, then O = diag(correction) O + P V.
  No score rows are stored. Rust pads the query buffer to a multiple of 8
  rows; rows >= T get P = 0 and are never written.
- Metal, T > 1, other head_dim (<= 512, e.g. the tiny fixture):
  `attention_flash`, the same online softmax with one SIMD group per
  (row, head) and scalar dot products.

The online softmax and matrix tiles change the summation order relative to
the 3-pass read, so chunked prefill matches token-by-token prefill within
tolerance, not bitwise (as already true for the tiled GEMM of ADR 0006).

Rejected: storing T x heads x capacity score rows (128 x 8 x 32k floats per
layer is too large); a scalar flash kernel with 8-position blocks (slower on
M5: 45 s vs 36 s at 10141 tokens, register pressure).

## Consequences

M5, BF16 weights, chunk 128, single runs: prefill 344 -> 715 tok/s at 2644
tokens and 88 s -> 18.3 s (115 -> 555 tok/s) at 10141 tokens; decode
unchanged. Generated tokens are identical to the ADR 0006 runs. The
2048-token long check passes with the same max error (3.2e-4); device
prefill 5.67 s -> 3.48 s. `device_real` now compares chunks 7/64/128 with
chunk 1 on real weights (head_dim 256 path). Not done: decode-side split-K
attention for very long contexts, fused kernels, a ROCm batched kernel.
