# ADR 0023: verify pass on the device engines; its cost on Metal

Update: ADR 0024 removed the per-token cost of 2-7 rows (fixed-count GEMV);
the guess below about X re-reads turned out wrong.

Status: accepted (measurement; speculative decoding itself is not built).
See spec/measurements/metal-m5-verify.json, ADR 0022 and spec/roadmap.md item 3.

## Context

ADR 0022 measured how often the MTP head's drafts are right (68 % / 43 % /
27 % for drafts 1-3 on CPU). Whether speculative decoding pays off on a GPU
also depends on the verify pass: one forward over the accepted token plus k
drafts, with vocabulary logits for every row. The idea assumes this costs
about one decode step, because decode is bound by reading the weights. We
had no way to compute logits for more than the last row.

## Decision

- `DeviceRun::verify(ids)` (src/device.rs): one forward over 1..=8 tokens
  (`VERIFY_ROWS`) that returns logits for every row. The final norm runs on
  all rows and the tied embedding projects them together, so the 509 MB
  vocabulary matrix is read once. `forward` takes the number of logit rows
  (0 = prefill chunk, 1 = last row, t = every row); the logits buffer holds 8
  rows (7.6 MiB more per run, counted in `run_bytes`).
- The 1-row path reads back exactly one vocabulary row. (The first version
  read the whole 8-row buffer, so `step` returned stale rows after a verify;
  the new GPU test caught it.)
- `<engine>-verify` (src/device/cli.rs) times, after N raw tokens and from
  one checkpoint, a decode step, `verify` over 1..=rows tokens and the
  DeltaNet checkpoint/restore (median of `--runs`), and compares each verify
  row with the same tokens decoded one at a time.
- `device_real_verify` (tests/device_gpu.rs): 1 row equals the decode step
  bitwise; 2..8 rows match sequential steps within the real-weight tolerance
  with the same greedy tokens; a step after a verify continues correctly.

## Consequences

M5, default kernels, median of 15 runs (ms; ratio to one decode step):

| context | decode | 2 rows | 3 | 4 | 5 | 8 | checkpoint | restore |
|---|---|---|---|---|---|---|---|---|
| 454 | 13.96 | 15.18 (1.09) | 16.19 (1.16) | 18.21 (1.31) | 20.18 (1.45) | 23.42 (1.68) | 1.65 | 1.42 |
| 2644 | 14.71 | 16.97 (1.15) | 18.63 (1.27) | 20.50 (1.39) | 22.56 (1.53) | 25.88 (1.76) | 1.64 | 1.43 |
| 8192 | 15.69 | 23.03 (1.47) | 24.68 (1.57) | 26.54 (1.69) | 28.73 (1.83) | 32.12 (2.05) | 1.66 | 1.45 |

- Values: argmax equal on every row; max logit difference 4.4e-5
  (summation order only). One row is the decode step bitwise.
- Each extra row adds about 2 ms, even at a 16-token context (13.9 ms ->
  14.4 / 15.7 / 17.7 for 2/3/4 rows) and with level-2 kernels, so it is
  not attention. Below 8 tokens the projections use `gemv_bf16` /
  `gemv_bf16_group`, which read each weight once but every row of X once per
  token from cache (`gemm_rows`, matmul.metal): about 4 bytes x 0.75 G
  multiply-adds per token. This is the likely cause, not yet profiled.
- At 8192 the jump from 1 to 2 rows (+7 ms) is probably the chunked
  attention path replacing the decode attention (`attention_split_grp`, ADR 0017).
- The DeltaNet checkpoint is a host copy of about 19 MB (1.65 ms, ~12 % of a
  decode step). A device-side copy should take about 0.2 ms.

Estimated speedup of MTP speculative decoding with these numbers (not
measured end to end; ADR 0022 acceptance; checkpoint every pass, restore on
rejection):

| context | full vocabulary, k = 1 / 2 / 3 | draft vocabulary ~32k, k = 1 / 2 / 3 |
|---|---|---|
| 454 | 1.05 / 1.02 / 0.91 | 1.29 / 1.43 / 1.40 |
| 2644 | 1.01 / 0.97 / 0.89 | 1.23 / 1.34 / 1.33 |
| 8192 | 0.85 / 0.86 / 0.80 | 1.01 / 1.13 / 1.15 |

With today's kernels it does not pay off with the full vocabulary. It would
need three things, in this order of effect:
1. a draft over a subset of the vocabulary (the main model still verifies
   every token, so the output is unchanged);
2. a multi-token GEMV that loads each X row once per threadgroup (e.g.
   through threadgroup memory), so 2-4 rows cost about one decode step;
3. decode attention for 2-8 query rows, and a device-side DeltaNet copy.

With 2 and 3 done (verify at ~1.0 and a 0.1 ms copy), the estimate for a
subset draft and k = 3 is 2.38 / (1.0 + 0.21 + 0.01) ≈ 1.95x.

## ROCm (issue #30)

`rocm-verify` is the same code (shared Rust engine); the HIP bridge did not
change. On the RX 7900 XTX (WSL2) the GPU tests pass, including
`device_real_verify`. The `--ids` check gives 1364 records with a max of
1.52e-4, as in ADR 0019. Decode speed and the generated tokens did not change
from main before PR #29: for example, 331 tokens gave 324.8-339.4 token/s
against 327.4-335.9, and 9872 tokens gave 292-295 against 292-298, with the
same tokens in every run. See spec/measurements/rocm-7900xtx-verify.json.

Median of 15 runs (ms; ratio to one decode step). 16 is an extra short
context:

| context | decode | 2 rows | 3 | 4 | 5 | 8 | checkpoint | restore |
|---|---|---|---|---|---|---|---|---|
| 16 | 3.78 | 5.44 (1.44) | 5.59 (1.48) | 5.87 (1.56) | 6.07 (1.61) | 8.03 (2.13) | 7.34 | 7.12 |
| 454 | 3.82 | 6.27 (1.64) | 6.16 (1.61) | 6.47 (1.69) | 6.81 (1.78) | 8.09 (2.12) | 7.25 | 6.90 |
| 2644 | 3.86 | 7.68 (1.99) | 7.30 (1.89) | 7.74 (2.00) | 7.76 (2.01) | 9.44 (2.44) | 6.56 | 6.30 |
| 8192 | 4.46 | 12.29 (2.76) | 11.77 (2.64) | 12.84 (2.88) | 12.36 (2.77) | 14.38 (3.22) | 8.79 | 9.52 |

- Values: argmax is equal on every row. The max logit difference is
  1.0e-5. One row is the decode step bitwise.
- The shape differs from Metal's. Extra rows are cheap, about 0.2-0.3 ms
  each from 2 to 7 rows. On ROCm, 8 rows still take the GEMV (GEMM starts at
  16 tokens), so 8 rows show no jump. Instead there is a constant step from
  1 to 2 rows: +1.7 ms at a 16-token context and +2.4 ms at 454 tokens, so it
  is not attention.
- Profile at 454 tokens (`QWEN_ROCM_PROFILE`, `--rows 2` minus `--rows 1`):
  - A 2-row verify makes about 180 bridge calls against 129 for decode.
    With more than one token there is no GEMV + Add + RmsNorm tail (ADR 0019
    item 10), so Add + RmsNorm runs separately.
  - Its warm kernel times (repeat mode) add up to about 2.5 ms, close to a
    decode step, but the wall time is 6.3 ms.
  - The vocabulary GEMV costs the same for 1 and 2 rows (578 / 573 us).
  - The 2-row kernels (`gemv_bf16_rows`, t2) are only slightly slower than
    the 1-token ones when warm.
  - So the step lies outside the warm kernel throughput. Candidates are the
    per-dispatch cost of the generic multi-token kernels (ADR 0019: kernel
    size costs time on WSL2), cold weights and the extra dispatches.
    Issue #32 (fixed token count, ADR 0024) tests the first.
- At 8192 the step from 1 to 2 rows is +7.8 ms, as on Metal. The chunk
  attention path (`attention_read`, 73 us warm per layer at 454 tokens,
  against 15 us for the decode one) replaces the decode attention.
- The DeltaNet checkpoint and restore are host copies of about 19 MB. They
  take 6.3-9.5 ms each, about 1.7-2.1 decode steps; on Metal they take
  about 0.1 of a step. On WSL2 this is the largest cost for speculative
  decoding, before the verify itself.

With these numbers MTP speculative decoding would be slower on ROCm. For
k = 3, the 2.38 tokens accepted per pass cost a 4-row verify (1.69) plus a
checkpoint (1.90), which is more than 3.5 decode steps before the draft
runs. On ROCm, in order:
1. a device-side DeltaNet checkpoint and restore;
2. the 1-to-2-row step. #32 (ADR 0024, ROCm section) took 0.3-0.6 ms off
   it. What is left is mostly the separate Add + RmsNorm (no multi-row
   tail), the chunk attention and host-side dispatches;
3. decode attention for 2-8 query rows at long contexts.
