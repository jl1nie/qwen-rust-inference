# ADR 0017: position-parallel decode attention (Metal)

Status: accepted; passed on Apple M5 (macOS 27.3). See
spec/measurements/metal-m5-decode-attention.json. CPU reference remains the
oracle; ABI v3 unchanged; HIP unaffected.

## Context

At 10141 tokens, Metal decoded at 50 token/s against MLX's 74. A decode
profile (64 tokens minus 1, one command buffer per dispatch) put the
attention read (ADR 0008's split kernel plus combine) first, at 5.8 ms per
token. The KV a token reads at that length is 6 layers x 41.5 MB = 249 MB,
about 1.9 ms at the measured 130 GB/s, so the kernel ran at about 3x the
bandwidth bound. The format (FP32 KV) was not the problem.

attention_split processed one position at a time per SIMD group: a
`simd_sum` and two `exp` per position on the critical path, the G = 4 heads of
a KV head each re-reading the same K/V, and 32-position splits (about 630
threadgroups and partial results per layer at 10k).

## Decision

- `attention_split_grp<D, 4>` (D = 64/128/256, G = 4):
  - One SIMD group per (split, KV head) serves all 4 query heads, so every
    K/V element loaded is used 4 times.
  - Positions go 32 at a time, one per lane: the lane computes its position's
    dot products for the 4 heads with float4 K loads.
  - The softmax max and sum are taken once per 32 positions (`simd_max` /
    `simd_sum`).
  - For P V, lanes own dimensions (lane + 32e) and the weights are broadcast
    with `simd_shuffle`.
  - Same partial layout (m, l, acc), so `attention_combine` is unchanged.
- `attention_split_par`: the same position-parallel scheme with one SIMD
  group per head, for other G (head_dim a multiple of 8, <= 512). Other
  shapes (the tiny fixture) keep attention_split.
- Span: about 40 splits, i.e. ceil(length/40) rounded up to a multiple of 32
  and clamped to 32..256. Still at least what the scratch row can hold
  (unchanged sizing). Measured best per length on M5: 32 at 454 positions,
  64 at 2644, 256 at 10141.
- Only the summation order changes (ADR 0004 tolerances).

## Consequences

M5 decode, 64 new tokens, 2 runs:

| prompt | before | after | MLX BF16 |
|---|---|---|---|
| 454 | 66.5-66.9 tok/s | 68.7-69.3 | 80.3 |
| 2644 | 62.9 | 67.0-67.1 | 76.9 |
| 10141 | 49.7-50.0 | 60.4-61.2 (+22 %) | 74.0 |

- Profiled attention at 10141 tokens: 5.8 -> about 3.8 ms per token with
  the per-head position-parallel kernel; the grouped kernel is faster still
  (end-to-end above).
- Generated tokens are identical on all prompts. A 1267-token prompt
  generates the same text as the CPU engine.
- The `--ids` check (token-by-token, full capture) and the GPU tests pass.

Rejected: span 512 (slower everywhere), and 8 heads' worth of registers
(G = 4 is this model).

Not done: 16-bit KV (lossy). It would halve the remaining KV traffic,
about 1 ms per token at 10k.
