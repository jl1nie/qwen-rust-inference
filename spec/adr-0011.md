# ADR 0011: chat, snapshots, a system-prefix cache, edits and traces in device chat

Status: experimental; passed on Apple M5 (macOS 27.3), Metal engine, and on
the CPU test bridge. ROCm shares the code but is not GPU-verified. ABI and
kernels are unchanged (v3). CPU reference remains the oracle. See
spec/measurements/metal-m5-chat.json.

## Context

The CPU `chat` (src/chat.rs) keeps one rewind point (the anchor, at the end
of the last user message) because the official template drops earlier
thinking, and saves conversations with src/snapshot.rs. The device engines
had single-run `infer` only, so a second question re-prefilled the whole
history, and a long document had to be prefilled again for every question
(3.6 s for 2637 tokens on M5).

## Decision 1: rewind = DeltaNet copy + position

On a hybrid model, attention KV can be kept for any prefix, but a DeltaNet
layer's state is one fixed-size matrix that has absorbed every later token
and cannot be cut back. `DeviceRun::checkpoint` therefore copies only the
DeltaNet conv/recurrent state to the host (about 19 MiB for Qwen3.5-0.8B:
18 layers x 1 MiB recurrent matrix plus conv history, independent of length); `restore` writes it back and moves the position
back. KV rows below the checkpoint are untouched as long as the run only
moved forward since then, which holds for every rewind point we keep
(each is a prefix of the live tokens). No device-to-device copy, no ABI
change. `initial_checkpoint` (zeros at 0) starts a new conversation without
reallocating. Rejected: periodic checkpoints for arbitrary-prefix reuse
(19 MiB each) and copying KV per checkpoint.

## Decision 2: same chat logic, same snapshot file

`DeviceChat` (src/device/chat.rs) is `ChatSession::user_turn` with the
device as engine: the same template rendering, anchor choice, pending-token
handling, sampling (`generate::select`, seeded or greedy) and `Turn`
statistics. It converts to and from `ChatSession` (`to_session` reads all
state with `inspect_state`; `from_session` uploads it with `load_state`), so
`save_chat`/`load_chat` and all their validation are reused unchanged. A chat
saved on the GPU resumes on the CPU and vice versa. The loaded anchor must
equal the live state cut to its position, because the device reuses the
live KV rows for it. A turn longer than `--capacity` is rejected before
anything changes; a device error poisons the run until `/reset`.

## Decision 3: prime the system message

`ChatSession::prime` / `DeviceChat::prime` prefill the system message alone
(`text::render_system`, the exact prefix `render_chat` emits), so later turns
reuse it, `/reset` returns to it, and a snapshot taken right after it is a
cache of a long system document. `load_chat` accepts that primed-only state
only when its tokens equal the encoded system prefix. `chat` primes unless
`--no-cache`; `--system-file` reads the message from a file.

## Decision 4: edits during a chat recompute the history

The edit is part of the computed state, so it is stored with it:
`InferenceSession` carries an optional `EditManifest` (validated as in
`infer`) used by every step, and the snapshot header gets an optional
`edit` field (absent in older files; older binaries reject edited files via
`deny_unknown_fields` rather than resuming them unedited). Changing the edit
mid-conversation (`ChatSession::set_edit`, `DeviceChat::set_edit`, `/edit
PATH|off`, `--edit` also after `--load-state`) recomputes the same token
history under the new edit from position 0, re-taking the system and anchor
checkpoints on the way; messages, the pending token and the RNG stay. So the
cached states never mix two edits, and `/edit off` returns exactly to the
unedited numbers. Rejected: keeping old states (the reuse would silently mix
edits) or dropping the history (breaks `/continue` and snapshot checks).

## Decision 5: traces at absolute positions

`--trace PATH --trace-position N,M,...` (plus `/trace N`, `/trace +K` in the
REPL) observe absolute positions. `DeviceChat` runs an observed position
alone with captures whenever it is computed (prefill, generation, or a
recomputation after a rewind or an edit change) and passes the step to an
observer; the CLI writes the ADR 0010 records, with `run_id` ending in
`-passN` (N counts turns, loads and edit changes) so a position computed
again is distinguishable. A trace error (e.g. the byte limit) stops tracing,
not the chat.

CPU `chat` takes the same options. `InferenceSession` accepts a
`session::Watch` (`wants(position)` + `observe(position, activations)`): only
wanted positions run the full observable step, the rest stay on the compact
step, so tracing a few positions of a long chat costs little. `ChatSession`
has `_watched` variants of prime, user turn, continue and set_edit, and the
CLI advances the pass number at the same points as device chat. CPU records
include the mixer internals (Q/K/V, attention scores and probabilities,
DeltaNet internals, FFN gate/up/SiLU) that device traces lack.

## Consequences

M5, BF16: a 2637-token system document is prefilled once (3.6 s) and saved
(86 MB); loading it takes 0.24 s and a 21-token question plus 48 generated
tokens 0.92 s, against 4.46 s without the cache, with the same output. Two
short turns: 188 / 167 ms on Metal vs 1.6 / 2.4 s on the CPU, same IDs and
reuse counts (reused 16, prefill 36). Snapshots moved Metal -> CPU and
CPU -> Metal and continued identically. The CPU-bridge test compares IDs,
reuse counts and full state of every turn with the CPU chat, plus resume in
both directions, reset to the primed state and a primed-only snapshot.
Edits (zeroing half of the FFN units of layers 1-2): Metal and CPU chat gave
the same changed answers over two turns; `/edit PATH` then `/edit off`
(23 positions recomputed each) reproduced the unedited answer; an edited
Metal snapshot continued identically on the CPU with its edit. A chat trace of
layer 3 at position 19 matched the CPU `infer` trace within 4e-5 on every
record. The same two-turn chat traced at positions 19, 21 and (via `/trace
+2`) 25 on the CPU and on Metal gave the same positions and passes; the 55
common records differ by at most 1.1e-4 (final_norm), and the CPU file adds
15 attention/FFN internal operations. Not done: KV in BF16 for smaller
snapshots.
