# ADR 0032: greedy picks on the device on ROCm (port of ADR 0030/0031); speculative decoding pays off

Status: accepted. See spec/measurements/rocm-7900xtx-device-argmax.json,
issue #44, ADR 0029, 0030 and 0031.

## Context

After ADR 0029, `rocm-speculative` generated the same IDs as greedy but ran
at 0.87-0.99x. Issue #44 listed three changes, in the expected order of
effect:

1. the device argmax of ADR 0030/0031 (op 16 `Argmax`, op 17
   `EmbedBf16Picked`, `qr_argmax`). Rust already uses it when the bridge
   advertises it. Without it, every verify row read back about 1 MB of
   logits, and every MTP head step needed a sync;
2. a GEMV + Add + RmsNorm tail for 2-8 rows;
3. one decode attention launch for 2-4 rows instead of one per row.

## Decision

- **`qr_argmax` = 2 on the HIP bridge and the CPU test bridge.**
  - Op 16 `Argmax` is the `argmax_rows` kernel (kernels.h), with one
    256-thread block per row. Each thread scans its elements in increasing
    index order and keeps the first maximum. The wave and block reductions
    take the larger value, with ties going to the smaller index. This is
    `generate::select`'s greedy rule. The kernel writes [index, number of
    non-finite values] per row, as on Metal.
  - Op 17 `EmbedBf16Picked` runs on `reference_kernel` (one thread per
    element, `body()` in reference.h). Output row r is row picks[2r] of the
    BF16 matrix.
  - Ops 16 and 17 are advertised by `qr_argmax`, not by `qr_max_op` (still
    15). The CPU test bridge runs both in `body()`.
- **Test.** New `cpu_bridge_argmax_matches_host_select` (src/device/tests.rs):
  - `step_greedy` equals `select` over `step`'s logits;
  - `verify_rollback_greedy` for 1-4 rows equals `select` over
    `verify_rollback`;
  - `EmbedBf16Picked` equals `EmbedBf16` of the picked rows.

  CI now runs the device-argmax paths on the CPU test bridge.
- **Rejected: the multi-row GEMV + Add + RmsNorm tail (item 2).** We built
  it as an optional `qr_gemm_bf16_add_norm_rows`. It was
  `gemv_bf16_wave_t<NB>`, and its last block ran Add + RmsNorm on the NB
  rows in `add_rms_norm_block`'s order. It was bitwise equal (same
  `logits_sha256`; 2-4 rows still 0 away from decode). It removed 47
  dispatches per verify pass, but it was not faster:
  - `rocm-verify` at 454 tokens: 2-3 rows went from 5.0-5.3 ms to 5.0-5.5 ms,
    so no faster and up to 0.2 ms slower.
  - `rocm-speculative`, k = 2: 423 tok/s against 430 without the tail.
  - Spreading the rows over waves (one row per wave, lane w playing threads
    w + 32 i to keep the order) cost 0.6 ms more per pass.

  The last block's serial norms, which read other blocks' rows with
  agent-scope loads, cost as much as the separate `add_rms_norm` dispatches
  they replace. Unlike decode (ADR 0019 item 10), the tail does not pay off
  for more than one row.
- **Not built: one attention launch for 2-4 rows (item 3).** As an upper
  bound, we ran a probe that runs the decode attention for row 0 only
  (wrong values, timing only). It saved 0.1-0.25 ms per verify pass with
  3-4 rows at 454 tokens. A merged launch still does the work of every row,
  so it would save less. We left it for later.

## Consequences

**Speculative decoding.** RX 7900 XTX, `rocm-speculative`, 8 prompts, 128
new tokens, draft on the device, 8,192-row draft vocabulary, 2 runs each.
The IDs equal plain greedy in every run.

| depth | plain, device argmax (tok/s) | speculative (tok/s) | speedup | with `--no-fused-draft` | speedup vs host-argmax baseline |
|---|---|---|---|---|---|
| 1 | 335 | 404-412 | 1.21-1.23 | 1.10-1.11 | 1.29 |
| 2 | 335-338 | 428-438 | 1.28-1.30 | 1.17-1.18 | 1.37 |
| 3 | 332-341 | 415-425 | 1.25 | 1.04-1.10 | 1.31 |

ADR 0029 had 0.90-0.97x with the same vocabulary.

- Per pass with k = 2: the verify, plus the head absorbing the pairs, takes
  4.0-4.1 ms. The chained drafts take 0.35 ms. A plain step takes 2.95 ms.
  The verify is about 1.37 decode steps (about 1.5 before), and a pass about
  1.5 steps for 1.91 tokens.
- Fused drafts (ADR 0031) matter more here than on Metal. Without them the
  drafts cost 1.1-1.8 ms per pass, because each MTP head step syncs. On WSL2
  a sync costs a lot.

**Greedy decode.** `rocm-infer` (greedy, `step_greedy` since ADR 0031) reads
2 floats per token instead of the full logits. Same Rust binary, main's
bridge against this one, 3 runs each, alternated:

| prompt (tokens) | main (tok/s) | this change (tok/s) |
|---|---|---|
| 13 | 270-284 | 276-298 |
| 331 | 304-320 | 334-337 |
| 2060 | 309-315 | 322-329 |

- That is about 4-6% faster. The generated IDs are identical in all runs.
- `rocm-chat` gives the same turns as issue #18: 1+1=2, 2+1=3, and CPU
  `--load-state` of the ROCm snapshot gives 3×2=6.

**Values.** The forward pass is unchanged. Only where the argmax is taken
changes, and its rule is the same. All 6 GPU tests pass, including
`device_real_rollback` (`verify_rollback_greedy` against `select`) and
`device_real_speculative` (`step_greedy`; fused against unfused drafts).

**What is left.** A 3-row verify still costs about 1.37 decode steps
(Metal: about 1.0). Neither fewer dispatches (the rejected tail) nor less
attention work moved it much. The rest is spread over the multi-row kernels
and the host side, and needs a profile per pass before more kernel work.
