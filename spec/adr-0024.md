# ADR 0024: GEMV with the token count fixed at compile time for 2-7 tokens (Metal)

Status: accepted. See spec/measurements/metal-m5-fixed-gemv.json and ADR 0023.

## Context

ADR 0023 measured the verify pass of speculative decoding on Metal: every
extra token added about 2 ms (454-token context: 2/3/4 rows = 1.09/1.16/1.31
decode steps), even at a 16-token context, so it was not attention. With
fewer than 8 tokens the projections run `gemv_bf16` / `gemv_bf16_group`
(`gemm_rows`, matmul.metal), which read each weight once.

ADR 0023 guessed that the cost was X being re-read once per token from cache.
A per-dispatch GPU timing (a temporary bridge patch, not kept) showed that
the GEMVs did grow with the token count (about +2.3 ms of GPU time from 2 to
4 rows), but these did not help (454 tokens, ms for 1-8 rows,
measurements file):

- 4 rows per SIMD group, reusing each X load for 4 rows: 4 rows 18.1 ->
  17.7 ms. So X traffic was not the cost.
- Same with FMA accumulation (fewer ALU instructions): 17.7 ms. So it was not
  ALU throughput either.
- `matmul2d` with 8-token x 64-row tiles: flat but slow, 19.0-20.0 ms for 2-7
  rows (decode is 14 ms).
- 8x8 simdgroup tiles of 128 rows x 8 tokens through threadgroup memory:
  31 ms.

The cause was the shape of the code. `gemm_rows` loops over the tokens up to
a runtime count, in passes of 8 with `if (b < nb)`, so its `sum[8]` array and
the per-token X loads were not fully unrolled. With the count fixed at
compile time, 2-7 tokens took 14.6-15.3 ms.

## Decision

- `gemm_rows_fixed<NB>` (matmul.metal) is `gemm_rows` with NB fixed and the
  token loops fully unrolled: same lanes, same column order, same pairwise
  float4 sums, then `simd_sum`. Kernels `gemv_bf16_t{2..7}` and
  `gemv_bf16_group_t{2..7}` (the grouped projections of ADR 0020).
- The bridge uses them at level 2 and above for 2-7 tokens with
  vector-aligned BF16 rows (`fixed_gemv`). Otherwise, and at level 1, it uses
  `gemv_bf16` / `gemv_bf16_group` as before. One token stays on `gemm_rows`:
  a fixed NB = 1 kernel measured no faster (14.07 vs 13.98 ms).
- The outputs are bitwise equal to the previous kernels.
  `metal-verify` now prints a SHA-256 of each verify result
  (`logits_sha256`); at 454 tokens all eight row counts match.
- These kernels also serve prefill chunks of 2-7 tokens (the end of a
  prompt, chat turns), with the same bits as before.

## Consequences

M5, default kernels, median of 15 runs, verify time as a ratio to one decode
step (before = ADR 0023):

| context | 2 rows | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|
| 454 | 1.05 (1.09) | 1.07 (1.16) | 1.06 (1.31) | 1.04 (1.45) | 1.05 (1.61) | 1.10 (1.75) | 1.69 |
| 2644 | 1.21 (1.15) | 1.21 (1.27) | 1.19 (1.39) | 1.17 (1.53) | 1.18 (1.71) | 1.22 (1.85) | 1.79 |
| 8192 | 1.49 (1.47) | 1.50 (1.57) | 1.47 (1.69) | 1.48 (1.83) | 1.49 (1.97) | 1.52 (2.10) | 2.04 |

- 2-7 rows now cost about the same as one another. At 454 tokens a verify
  pass is within 4-10 % of a decode step.
- What is left at long contexts is a constant step from 1 to 2 rows: +3 ms
  at 2644 and +7.7 ms at 8192. It is probably the prefill attention path
  (`attention_tensor`), which serves 2 or more query rows instead of the
  decode attention (`attention_split_grp`, ADR 0017).
- 8 rows is unchanged: 8 or more tokens take the prefill GEMMs
  (`gemm_tensor_*`, 32-token tiles).
- Decode and the generated tokens are unchanged. The GPU tests pass,
  including `device_real_verify`, `device_real_kernel_levels` and
  `device_real`. `device_real` covers prefill chunks of 7 tokens and a last
  chunk of 6 tokens.

Estimated speedup of MTP speculative decoding (same assumptions as ADR
0023; not measured end to end):

| context | full vocabulary, k = 1 / 2 / 3 | draft vocabulary ~32k, k = 1 / 2 / 3 |
|---|---|---|
| 454 | 1.07 / 1.07 / 1.01 (was 1.05 / 1.02 / 0.91) | 1.32 / 1.53 / 1.62 (was 1.29 / 1.43 / 1.40) |
| 2644 | 0.97 / 1.00 / 0.96 | 1.17 / 1.39 / 1.50 |
| 8192 | 0.84 / 0.88 / 0.86 | 0.99 / 1.18 / 1.28 |

Next, in order of effect:
1. a draft over a subset of the vocabulary;
2. decode attention for 2-8 query rows, which removes the step at long
   contexts;
3. a device-side DeltaNet copy (1.65 ms now, about 12 % of a decode step).
