# ADR 0014: opt-in 16-bit prefill attention on RDNA3 (ROCm)

Status: experimental, opt-in (`--attention-f16`); passed on RX 7900 XTX
(gfx1100), WSL2, ROCm 7.2.4 at its own tolerance. See
spec/measurements/rocm-7900xtx-attention-f16.json. The default stays FP32
(ADR 0013); CPU reference remains the oracle.

## Context

After ADR 0013 the FP32 flash attention was at most about a third of
prefill time at 10k tokens. RDNA3's matrix instructions (WMMA) take only
FP16/BF16 inputs. Until now every device path changed only the summation
order, never a value (ADR 0006: lossless formats only), so a 16-bit path
needs its own decision, tolerance and an explicit switch.

## Decision

- Option, not default: `rocm-check/rocm-infer/rocm-chat --attention-f16`
  -> `DeviceModel::set_attention_f16` -> optional bridge symbol
  `qr_set_option(ctx, "attention_f16", 1)`. No ABI bump. A bridge without
  the symbol (Metal, older builds) or one that cannot do it (CPU test bridge)
  returns an error; unsupported shapes (head_dim not a multiple of 16 or >
  256, 16 not divisible by heads/kv) fail at the first prefill. Nothing falls
  back to FP32 silently. Reports record `"attention": "f16_prefill"`.
- Scope: chunked prefill (T > 1) only. Decode keeps the FP32 split kernel:
  with one query row a 16x16 tile is mostly idle and decode attention is
  bound by reading the FP32 KV cache. The KV cache, snapshots, softmax
  statistics and O stay FP32, so saved states stay compatible.
- Kernel `attention_wmma` (`v_wmma_f32_16x16x16_f16`, FP32 accumulate):
  a block holds 16 query vectors (16/G rows x the G query heads of one KV
  head); Q (pre-scaled by 1/sqrt(d)) is staged in LDS as FP16; per 16
  positions S = Q K^T, causal mask, online softmax per row (in the C
  fragment layout, reductions over the 16 lanes of a half-wave), P to LDS as
  FP16, O += P V. head_dim 256 is split over 4 waves (one wave with 16
  output tiles spilled 511 VGPRs); their partial S are summed in LDS in a
  fixed order. Positions are split into spans of 256 (grid z) whose
  partials go to a bridge-owned buffer and are merged by the generalised
  `attention_combine`.
- FP16, not BF16: Q/K are RMS-normalised and V and P are small, so range is
  not a concern, while FP16 keeps 3 more mantissa bits.
- Fragment layouts were checked on the GPU first with identity/unique
  matrices (A: lane = row, B: lane = column, C: element i of lane l is row
  2i + l/16). The same probe showed that WMMA's FP32 accumulation is not
  exact even for small integers (5 -> 5.0000024), negligible next to the
  FP16 rounding.
- Tolerance (ADR 0004 had 3e-3 for real weights): atol = rtol = 2e-2,
  about 2.3x the worst measured error, plus the existing requirement that
  the greedy token matches at every long-check boundary. With the FP32
  tolerance the long check fails at position 31 (3.47e-3).

## Consequences

| check | FP32 (ADR 0013) | 16-bit |
|---|---|---|
| `--ids 16,10,16,28` max abs error | 1.43e-4 | 8.86e-3 |
| 2048-token long check max abs error | 2.64e-4 | 7.96e-3 (cosine >= 0.99999992, top-1 equal at all 21 boundaries) |

Prefill, medians of 3 runs (64 generated tokens identical to FP32 on every
input): 331 tokens 0.115 -> 0.116 s, 1267 0.388 -> 0.375 s, 2060 0.652 ->
0.605 s (1.08x), 9758 4.42 -> 3.18 s (1.39x). Decode unchanged.

The gain is limited because attention is only part of prefill and RDNA3's
FP16 matrix rate is only about twice its FP32 FMA rate. It grows with the
context; below ~1k tokens it is noise. Worth it only for long documents,
and only when the larger deviation is acceptable.

Not done: 16-bit KV cache (would halve decode KV traffic but changes
snapshots), WMMA projections (needs 16-bit activations), Metal (has FP32
matrix tiles already, ADR 0007).
