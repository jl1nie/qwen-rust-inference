# ADR 0013: ROCm kernels with a GPU decomposition; parallel CPU projections

Status: experimental; passed on RX 7900 XTX (gfx1100), Windows 11 + WSL2
Ubuntu 24.04, ROCm 7.2.4. See spec/measurements/rocm-7900xtx.json. CPU
reference remains the oracle and ADR 0004 tolerances are unchanged. ABI v3
and the Rust device engine are unchanged, so Metal is unaffected.

## Context

The first run of the HIP bridge on real hardware (same day, before this ADR)
was correct but unusable for long inputs: 2060 prompt tokens took 431 s to
prefill (5 tok/s) and decoded at 2.2 tok/s, slower than the CPU engine,
while the GPU's compute utilisation stayed near 0%.

Analysis:
1. Every HIP op ran the CPU test bridge's scalar body: one GPU thread per
   element, head, group or column, no shared memory, no barriers. That
   constraint (stated in the old bridge: "CPU arithmetic tests execute
   precisely this body") also fixed the GPU decomposition. AttentionRead ran
   8 threads (one per query head) for the whole GPU, each looping over the
   128-row chunk x all past positions x head_dim, with score rows in VRAM.
   RMSNorm over the hidden size was a single thread. DeltaRule re-read and
   re-wrote its state column in VRAM for every token.
2. BF16 projections launched one block per (row, token): a prefill chunk
   read the weights T times.
3. ADRs 0006 to 0009 improved Metal and were checked for the HIP/CPU body
   only by arithmetic tests ("results are the same"); nobody measured HIP
   speed, and the specs said so, but the gap was not visible until a run.
4. On WSL2 the HSA runtime finds the GPU only with
   HSA_ENABLE_DXG_DETECTION=1 (librocdxg via /dev/dxg); without it
   `rocminfo` reports "hsa_init Failed". This was not documented.
5. Process: the first benchmark ran fixed long inputs without a short
   length sweep or a glance at GPU utilisation, so the quadratic blow-up
   was found only after a 10-minute run on the longest input.

## Decision 1: separate the reference bodies from the GPU kernels

- `native/rocm/reference.h`: the scalar bodies, unchanged in arithmetic.
  The CPU test bridge (QR_CPU_TEST) runs only these; HIP uses them for the
  cheap elementwise ops (Add, SiluProduct, ConvSilu, DeltaQk, DeltaGates,
  AttentionQuery, AttentionKv, EmbedBf16) and as fallbacks for shapes the
  kernels do not cover (head_dim > 256, more than 8 query heads per KV head,
  key_dim > 128, rows not a multiple of 8 BF16 values).
- `native/rocm/kernels.h`: HIP-only kernels for the heavy ops.
- `native/rocm/bridge.cpp`: the C ABI and the dispatch between them.
The CPU bridge therefore no longer exercises the GPU decomposition; the
ignored GPU tests (`device_tiny`, `device_real`) and `rocm-check` do. The
tiny fixture (head_dim 4, key_dim 4, 8-column matrices) runs the same
templated kernels with guards, so it covers every kernel except the tiled
GEMM (needs >= 16 rows per chunk); `device_real` covers that.

## Decision 2: kernels (gfx1100, wave32)

- BF16 GEMV (decode, chunks < 16 rows): one wave per weight row, 16-byte
  loads (8 BF16) so a wave reads 512 contiguous bytes per step; up to 8
  token rows share each weight load; FMA, wave shuffle reduction.
- BF16 GEMM (chunks >= 16 rows): 64 weight rows x 32 tokens per block,
  32-column slices of W (widened to f32) and X staged in LDS, 4x2 outputs
  per thread. A 128-row chunk reads each weight 4 times instead of 128.
  RDNA3 WMMA takes FP16/BF16 for both operands; rounding the activations
  would make this lossy, so it stays FP32 FMA (ADR 0006: no value changes).
- RMSNorm: one block per group, block reduction (the ADR 0009 change).
- DeltaRule: a value column is owned by 4 adjacent lanes with 32 key rows
  each; the state stays in registers for the whole chunk (one VRAM read and
  write per chunk). The two key_dim dot products are combined by shuffles.
  One thread per column with 128 registers spilled (256 VGPRs, 35 spills).
- AttentionRead, prefill (T > 1): flash attention as in ADR 0007's
  attention_mma grouping. A block serves one KV head and 8 / G query rows
  (G = query heads per KV head), one wave per (row, query head). K and V of
  16 positions are staged in LDS once per step and shared by all waves.
  Each wave computes per-lane partial dot products for the 16 positions,
  reduces them with a butterfly (lane l ends with the score of position
  l / 2: 16 shuffles instead of 16 x 5), applies the causal mask, an online
  softmax update and adds P V from LDS. FP32 throughout (no FP32 matrix
  instructions on RDNA3, unlike Metal's simdgroup_float8x8).
- AttentionRead, decode (T = 1): the same kernel with one row per block and
  the positions split into about 64 spans per KV head (multiples of 32, the
  ATTENTION_SPLIT the Rust side sizes the n6 scratch for), merged by
  `attention_combine` (ADR 0008's flash-decoding). Falls back to one split
  if the scratch is too small.
- Explicit `fmaf` in the new kernels; `-ffp-contract=off` stays, so no other
  expression is contracted implicitly.

All of these reorder sums relative to the CPU reference (wave/block
reductions, tiles, online softmax), so device results match within the ADR
0004 tolerances, not bitwise, as on Metal.

## Decision 3: WSL2 device detection

`qr_create` sets HSA_ENABLE_DXG_DETECTION=1 before the first HIP call when
/dev/dxg exists and the variable is unset (a user value wins). The device
info string records `wsl_dxg=1`. spec/rocm.md documents the variable for
`rocminfo` and other tools.

## Decision 4: parallel CPU projections (src/parallel.rs)

Every `Matrix::linear`/`project` (Reference, Optimized and Vector) splits
its output rows into contiguous blocks; each block is computed by one
thread with the unchanged serial function, so every output keeps its
summation order and results are bit-identical for any thread count
(checked: generated text and full traces, 1 vs 8 threads). The sgemm path
splits at its existing 64-row BF16 widening blocks.

Starting scoped threads per projection (about 170 per decoded token) was
measured and rejected: 20.9 tok/s serial fell to 9.9 with 24 threads. A
persistent pool (std only: Mutex/Condvar, an atomic block counter, waiting
threads spin 100 us before sleeping) is used instead. Work below 2^15
multiply-adds per block stays on the caller; a second concurrent caller
(parallel tests, nesting) runs serially instead of waiting. One `unsafe`
erases the task lifetime; `run` returns only after every worker has left
the job. `QWEN_THREADS=N` overrides; the default is min(cores, 8).

## Consequences

RX 7900 XTX, BF16, chunk 128, 64 new tokens, medians of 3 runs (before =
the first HIP run with the reference kernels, 1 run):

| prompt | prefill before | prefill now | decode before | decode now |
|---|---|---|---|---|
| 4 tokens | 0.036 s | 0.015 s | 58.3 tok/s | 173 tok/s |
| 331 | 10.4 s | 0.115 s (2870 tok/s) | 11.2 | 176 |
| 1267 | 160 s | 0.388 s (3270 tok/s) | 3.5 | 175 |
| 2060 | 431 s | 0.652 s (3160 tok/s) | 2.2 | 169 |
| 9758 | (not finished) | 4.42 s (2210 tok/s) | - | 151 |

Generated tokens are identical to the before runs and across runs. On the
way, the per-wave attention without LDS (one wave per (row, head), K/V from
L2) gave 15.6 s / 107 tok/s at 9758 tokens; the LDS-tiled version 4.4 s /
151. Real-weight check max error 1.43e-4 (Metal 1.97e-4), 2048-token long
check 2.64e-4 (Metal 3.2e-4); `device_real` 45 s -> 10 s.

CPU engine (Vector, 4-token prompt, 32 decode steps): 21.0 tok/s serial,
26.7-27.1 with 2 to 8 threads. Decode reads the 1.5 GB of BF16 weights per
token, about 41 GB/s here, so it is memory-bandwidth bound and more threads
do not help. The CPU half of the 2048-token long check fell from 127 s to
105 s (the attention read and DeltaNet recurrence are still serial).

Not done:
- 16-bit attention (WMMA FP16/BF16): lossy, needs its own ADR, tolerances
  and an opt-in flag. At 9758 tokens attention is at most about a third of
  prefill; at 2k tokens much less.
- WMMA for the projections (needs BF16 activations: lossy, same reason).
- Kernel fusion, HIP graphs (decode is about 5.8 ms/token for ~1.5 GB of
  weights, i.e. about 260 GB/s of 960 GB/s; launch overhead not measured
  because rocprofv3 aborts under WSL2).
- Parallel CPU attention/DeltaNet heads.
