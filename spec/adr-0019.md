# ADR 0019: fewer, better-fed dispatches for ROCm decode

Status: accepted; passed on RX 7900 XTX (gfx1100), WSL2, ROCm 7.2.4. See
spec/measurements/rocm-7900xtx-decode.json (issue #19). Values change only
by summation order (ADR 0004 tolerances); generated tokens were identical
on every measured prompt.

## Context

After ADR 0013 decode took about 5.8 ms per token (~175 token/s). It reads
about 1.5 GB of weights per token, so it ran at ~260 GB/s, roughly a quarter
of the card's ~960 GB/s. `rocprofv3` crashes on WSL2, so there were no
per-kernel times.

## Measuring

The bridge gained an opt-in profiler, `QWEN_ROCM_PROFILE`:

- `repeat`: every bridge call is issued 1 + 20 times and the last 20 are
  timed back to back between one hipEvent pair. Event overhead (about 10 us
  per pair on WSL2, which made `=1` useless for small kernels) is spread
  over 20 dispatches. The repeats re-apply stateful ops, so the values of
  such a run are meaningless; the weights also stay in the 96 MB Infinity
  Cache, so GEMVs look faster than in a real step.
- `1`: one event pair per call (includes the event overhead).
- `host`: no events. It records the time between logit readbacks and how
  much of it the host spends waiting in the readback.

Standalone microbenchmarks (not kept in the repository) gave the floor:
back-to-back empty kernels cost 2.5 us each. HIP Graph replay costs 2.3 us
per node, because WSL2's `librocdxg` converts every AQL packet to PM4 on a
CPU thread. A launch followed by a sync takes 137 us, and the 1 MB logit
readback takes 155 us (pageable) or 127 us (pinned).

What the measurements showed, at the start (4-token prompt):

| | per token |
|---|---|
| bridge calls | 459 |
| GPU time, sum of `repeat` means | 3.94 ms |
| vocabulary projection 248320x1024 | 0.58 ms (~880 GB/s, already near the limit) |
| `delta_qk`, `attention_query`, `attention_kv` | 1.11 ms: still the reference bodies, one thread per head (16, 8 and 2 threads) |

With the readback counted as waiting (a pageable D2H copy already waits for
the queue), the host spends ~90% of a step waiting for the GPU. Enqueueing a
token takes about 0.4 ms. The bottleneck is therefore on the GPU side: kernel
time plus a few microseconds of gap per dispatch.

A cold GEMV, measured over about 1 GB of distinct weights, reached only
320-600 GB/s on the per-layer matrices. Each lane had one 16-byte load in
flight per loop step.

## Decision

1. **One wave per head** for DeltaQk, AttentionQuery and AttentionKv
   (`delta_qk_wave`, `attention_query_wave`, `attention_kv_wave`). The sums
   of squares are wave reductions. Every output element is the reference
   expression computed by one lane: the RoPE pair is normalized by the lane
   that rotates it.
2. **Grouped projections**: an optional bridge symbol
   `qr_gemm_bf16_group(ctx, n, items, x, cols, batch)` runs DeltaNet
   qkv/z/a/b and attention q/k/v in one dispatch. It covers fewer than 16
   tokens; larger chunks keep the tiled GEMM. Each row runs the same code
   as `gemv_bf16_wave` (shared `gemv_bf16_rows`), so the outputs are bitwise
   equal.
3. **Fused pairs**, advertised by the optional `qr_max_op` (11 without it):
   - op 12 `AddRmsNorm`: the residual add and the next RMSNorm, used after
     the mixer and, at a layer's end, with the next layer's input norm.
   - op 13 `RmsNormGate`: DeltaNet's RMSNorm and the SiLU gate.
   - optional `qr_gemm_bf16_glu`: FFN gate and up rows of the same index in
     one wave, then `silu(g) * u`.

   All three keep the reduction order of the ops they replace and are
   bitwise equal on the GPU and on the CPU test bridge. The test
   `cpu_bridge_fusions_match_separate_calls` checks this, and runs the whole
   forward with every fusion switched off.
4. **Four weight loads in flight** per lane in the BF16 GEMV and GLU loops
   (`kGemvLoads`). The pieces are still consumed in the order j = lane,
   lane + 32, ..., so the sums are bitwise unchanged. The cold-GEMV
   microbenchmark gave 321 -> 605 GB/s (3584x1024) and 478 -> 761 GB/s
   (6144x1024).
5. The layer output is added straight into `x`, dropping a buffer and a
   device copy per layer.
6. In the prefill attention kernel, K/V are staged with float4 copies and no
   per-element division (bitwise unchanged; at short context decode
   attention went from 31 to 23 us).

Calls per token: 459 -> 261. Bridges without the optional symbols (Metal,
older HIP builds) keep the previous calls; the Rust engine chooses per
symbol. No ABI bump.

## Result

| input | decode before -> after | prefill before -> after |
|---|---|---|
| 331 tokens | 173 -> 267 token/s | 0.118 -> 0.108 s |
| 1267 | 172 -> 261 | 0.398 -> 0.358 s |
| 2060 | 166 -> 255 | 0.667 -> 0.591 s |
| 9872 | 149 -> 228 | 4.45 -> 3.63 s |

These are medians of 3 runs. With a 4-token prompt, decode went from 175 to
272 token/s (5.7 -> 3.7 ms per token, ~400 GB/s effective). Generated
tokens are identical before and after. The `--ids` check gives 1.52e-4
(1.43e-4 before), the 2048-token long check 2.63e-4 (2.64e-4) and 8192
tokens 1.04e-3 (1.04e-3).

## Rejected

- HIP Graphs: no gain per node in the microbenchmark (above), and positions
  change every step, so the captured parameters would need updating.
- Split-K GEMV for the 1024-row matrices: no clear gain, and the bits
  change.
- A compact decode attention kernel with one lane per position: twice as
  slow, because each position becomes a dependent load-reduce-exp chain.
  The tiled kernel stays.
- More than 4 loads in flight: slower (register pressure).

## Remaining

At 3.7 ms per token, decode still waits on GPU work that is not weight
traffic. The ~260 dispatches cost a few microseconds each, the small
latency-bound kernels (decode attention ~23 us x 6, DeltaRule ~9 us x 18,
AddRmsNorm ~4 us x 48) add more, and the 1024-row GEMVs reach only
470-670 GB/s cold. Next candidates: fuse DeltaGates into DeltaRule
(needs dt and A_log in one buffer to fit the 8 pointer slots), fuse
AttentionQuery and AttentionKv, and a decode attention kernel with fewer
instructions that keeps 16 positions in flight. Run each candidate against
the same checks.
