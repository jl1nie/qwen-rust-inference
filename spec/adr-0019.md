# ADR 0019: fewer, better-fed dispatches for ROCm decode

Status: accepted; passed on RX 7900 XTX (gfx1100), WSL2, ROCm 7.2.4. See
spec/measurements/rocm-7900xtx-decode.json (issue #19). Values change only
by summation order (ADR 0004 tolerances); generated tokens were identical
on every measured prompt.

## Context

After ADR 0013 decode took about 5.8 ms per token (~175 token/s). It reads
about 1.5 GB of weights per token, so it ran at ~260 GB/s, roughly a quarter
of the card's ~960 GB/s. `rocprofv3` crashes on WSL2, so there were no
per-kernel times.

## Measuring

The bridge gained an opt-in profiler, `QWEN_ROCM_PROFILE`:

- `repeat`: every bridge call is issued 1 + 20 times and the last 20 are
  timed back to back between one hipEvent pair. Event overhead (about 10 us
  per pair on WSL2, which made `=1` useless for small kernels) is spread
  over 20 dispatches. The repeats re-apply stateful ops, so the values of
  such a run are meaningless; the weights also stay in the 96 MB Infinity
  Cache, so GEMVs look faster than in a real step.
- `1`: one event pair per call (includes the event overhead).
- `host`: no events. It records the time between logit readbacks and how
  much of it the host spends waiting in the readback.

Standalone microbenchmarks (not kept in the repository) gave the floor:
back-to-back empty kernels cost 2.5 us each. HIP Graph replay costs 2.3 us
per node, because WSL2's `librocdxg` converts every AQL packet to PM4 on a
CPU thread. A launch followed by a sync takes 137 us, and the 1 MB logit
readback takes 155 us (pageable) or 127 us (pinned).

What the measurements showed, at the start (4-token prompt):

| | per token |
|---|---|
| bridge calls | 459 |
| GPU time, sum of `repeat` means | 3.94 ms |
| vocabulary projection 248320x1024 | 0.58 ms (~880 GB/s, already near the limit) |
| `delta_qk`, `attention_query`, `attention_kv` | 1.11 ms: still the reference bodies, one thread per head (16, 8 and 2 threads) |

With the readback counted as waiting (a pageable D2H copy already waits for
the queue), the host spends ~90% of a step waiting for the GPU. Enqueueing a
token takes about 0.4 ms. The bottleneck is therefore on the GPU side: kernel
time plus a few microseconds of gap per dispatch.

A cold GEMV, measured over about 1 GB of distinct weights, reached only
320-600 GB/s on the per-layer matrices. Each lane had one 16-byte load in
flight per loop step.

## Decision

1. **One wave per head** for DeltaQk, AttentionQuery and AttentionKv
   (`delta_qk_wave`, `attention_query_wave`, `attention_kv_wave`). The sums
   of squares are wave reductions. Every output element is the reference
   expression computed by one lane: the RoPE pair is normalized by the lane
   that rotates it.
2. **Grouped projections**: an optional bridge symbol
   `qr_gemm_bf16_group(ctx, n, items, x, cols, batch)` runs DeltaNet
   qkv/z/a/b and attention q/k/v in one dispatch. It covers fewer than 16
   tokens; larger chunks keep the tiled GEMM. Each row runs the same code
   as `gemv_bf16_wave` (shared `gemv_bf16_rows`), so the outputs are bitwise
   equal.
3. **Fused pairs**, advertised by the optional `qr_max_op` (11 without it):
   - op 12 `AddRmsNorm`: the residual add and the next RMSNorm, used after
     the mixer and, at a layer's end, with the next layer's input norm.
   - op 13 `RmsNormGate`: DeltaNet's RMSNorm and the SiLU gate.
   - optional `qr_gemm_bf16_glu`: FFN gate and up rows of the same index in
     one wave, then `silu(g) * u`.

   All three keep the reduction order of the ops they replace and are
   bitwise equal on the GPU and on the CPU test bridge. The test
   `cpu_bridge_fusions_match_separate_calls` checks this, and runs the whole
   forward with every fusion switched off.
4. **Four weight loads in flight** per lane in the BF16 GEMV and GLU loops
   (`kGemvLoads`). The pieces are still consumed in the order j = lane,
   lane + 32, ..., so the sums are bitwise unchanged. The cold-GEMV
   microbenchmark gave 321 -> 605 GB/s (3584x1024) and 478 -> 761 GB/s
   (6144x1024).
5. The layer output is added straight into `x`, dropping a buffer and a
   device copy per layer.
6. In the prefill attention kernel, K/V are staged with float4 copies and no
   per-element division (bitwise unchanged; at short context decode
   attention went from 31 to 23 us).
7. **Smaller kernels.** Each dispatch appears to fetch its instructions
   anew. At length 1 the tiled attention took 11.4 / 13.6 / 21.7 us for
   head_dim 64 / 128 / 256, growing with code size although the work is
   tiny. So:
   - `attention_tiled<L, FULL>`: when head_dim == 32 L, the K/V block past
     the last position is zero-filled in LDS and the inner loops lose their
     bounds checks. A zero K row adds fmaf(q, 0, 0) = 0 to a masked score,
     and a zero V row adds fmaf(0, 0, acc) = acc, so results are bitwise
     unchanged.
   - `butterfly_sum` reads both values before selecting.
     `upper ? v[i] : v[i + count]` had compiled to a runtime register index:
     about 940 compare/select instructions.
   - Together these took the kernel from 5445 to 1889 lines of assembly.
     The microbenchmark went from 21.7 / 31.7 / 29.8 us to 11.1 / 15.5 /
     11.4 us at length 1 / 32 / 2048.
   - `delta_rule_registers<K, P, FULL>` (key_dim == K P) drops the per-row
     guards (about 130 branches) and reads q/k as float4.
8. **Two more fusions** (the 8 pointer slots of `Params` are the limit, so
   small weights are uploaded once more as one buffer):
   - op 14 `DeltaRuleGated`: DeltaRule computes its gates from a, b and
     `[dt | A_log]` with DeltaGates' expressions (`delta_gate` in
     reference.h).
   - op 15 `AttentionQueryKv`: AttentionQuery and AttentionKv in one
     dispatch with `[q_norm | k_norm]`. Each part runs its own op's code.

9. **One block per DeltaNet head.** An optional `qr_delta_mixer(ctx,
   const QrDelta*)` takes the slots of ConvSilu, DeltaQk, DeltaRuleGated and
   RmsNormGate. For at most 4 tokens, with key_heads == value_heads and
   head dims 128, it runs them as one block of 512 threads per value head,
   with barriers between the stages. Each stage runs the same per-item code
   as its op (`conv_silu_channel`, `delta_qk_item`, `delta_rule_column`).
   The final norm reproduces the 128-thread reduction of
   `rms_norm_gate_block` per group of 128 threads (`group_sum`). The four
   ops took ~17 us plus three gaps; the block takes 10.7 us. Longer chunks
   keep the four ops, which parallelize better.
10. **Add + RmsNorm in the tail of the GEMV that produces its input**
    (`qr_gemm_bf16_add_norm`, one token). This covers the mixer output
    projection, FFN down, and the final norm after the last layer. Every
    block writes its rows, fences and takes an atomic ticket. The last one
    computes the sum and norm with add_rms_norm_block's expressions,
    reading the other rows with device-scope loads, and resets the ticket.
    No block waits for another. FFN down + norm went from 8.0 + 4.2 to
    10.2 us, and the output projection + norm from 5.6 + 4.2 to 8.0 us.

11. **One-token GEMV kernels.** Item 2 made `gemv_bf16_rows` a shared
    function that the compiler did not inline. Called with its 8-token
    accumulators, a cold 1024x3584 GEMV took 16-23 us, against 10.4 us for a
    one-token specialization of the same loop (`gemv_rows_1`). Every
    one-token launch now uses it: plain, grouped, GLU and the add-norm tail.
    Each wave sums two rows (cold 3584x1024: 555 -> 719 GB/s; 1024x2048: 504
    -> 576 GB/s). Every row consumes its pieces in the same order, so the
    outputs are bitwise unchanged. Warm times: grouped 14.4 -> 9.8 us, GLU
    10.0 -> 7.5, FFN down + norm 10.2 -> 7.6, output projection + norm 8.0 ->
    6.5.

Calls per token: 459 -> 261 (items 1-6) -> 232 (item 8) -> 129 (items
9-10). Items 9-10 are used for one token without capture (decode); they
are bitwise equal to the separate calls. The CPU-bridge test covers that
path, and chat, edits and generated tokens are unchanged on the GPU. Bridges without the optional symbols (Metal,
older HIP builds) keep the previous calls; the Rust engine chooses per
symbol. No ABI bump.

## Result

| input | decode: before / 1-6 / 1-8 / 1-10 / all | prefill: before / 1-6 / all |
|---|---|---|
| 331 tokens | 173 / 267 / 290 / 317 / 324 token/s | 0.118 / 0.108 / 0.090 s |
| 1267 | 172 / 261 / 284 / 294 / 312 | 0.398 / 0.358 / 0.291 s |
| 2060 | 166 / 255 / 284 / 307 / 314 | 0.667 / 0.591 / 0.46 s |
| 9872 | 149 / 228 / 260 / 280 / 288 | 4.45 / 3.63 / 2.55 s |

These are medians of 3 runs; repeated runs vary by about 5%. With a 4-token
prompt, decode went from 175 to about 329 token/s (5.7 -> 3.0 ms per token,
~500 GB/s effective). Prefill gained
as well (1.7x at 9872 tokens), mostly from the smaller attention and
DeltaRule kernels. Generated tokens are identical at every stage. The `--ids` check gives 1.52e-4
(1.43e-4 before), the 2048-token long check 2.63e-4 (2.64e-4) and 8192
tokens 1.04e-3 (1.04e-3). Items 7-11 are bitwise equal to the stage
before them (same check results).

## Rejected

- HIP Graphs: no gain per node in the microbenchmark (above), and positions
  change every step, so the captured parameters would need updating.
- Split-K GEMV for the 1024-row matrices: no clear gain, and the bits
  change.
- A compact decode attention kernel with one lane per position: twice as
  slow, because each position becomes a dependent load-reduce-exp chain.
  The tiled kernel stays.
- More than 4 loads in flight: slower (register pressure).
- Folding DeltaGates into DeltaQk: together they need 9 pointer slots, and
  DeltaRule already reads the same rows.
- Folding Add + RmsNorm into the *next* projection: every block would
  recompute the norm before its GEMV (the grouped projection went from 14.5
  to 18.7 us, GLU from 9.9 to 14.4 us). That costs as much as the dispatch
  saved, even with the first weight loads issued before the norm.
  Persistent grids (96-768 blocks, norm once per block) were slower still,
  with too few loads in flight. Item 10 does the norm at the producer's
  tail instead.
- AttentionQueryKv in the last block of the q/k/v projection: 16.9 us
  against 7.2 + 7.8 us. Over three host-profile runs the step time did not
  change (3.19 vs 3.24 ms). The one block's serial work costs what the
  dispatch saved. The decode attention_combine in the attention kernel's
  last block has the same shape (one block doing all heads' merges), so it
  was not pursued.
- Non-temporal weight loads: within noise.

## Remaining

At about 3.0 ms per token, decode issues 129 dispatches. With no dispatches
at all, a step costs 0.23 ms of host work and readback. The 1.5 GB of
weights now run at about 700 GB/s in the per-layer GEMVs and 880 GB/s in
the vocabulary projection. The rest is the decode attention (~13 us x 6),
DeltaNet's head block (~11 us x 18) and the gaps between dispatches. Moving
small serial work into a projection's last block did not pay off (see
Rejected). What is left would need different algorithms rather than
fusions: a decode attention with fewer instructions per position, or a
DeltaNet head spread over more than one block.
