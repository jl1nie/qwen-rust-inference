# ADR 0018: Metal kernel levels (reference, simdgroup, tensor)

Status: accepted; passed on Apple M5 (macOS 27.3). Refactoring only: the
default path runs the same kernels with the same launch shapes, so results
are bit-identical to ADR 0017 and the speed is unchanged. See
spec/measurements/metal-m5-kernel-levels.json.

## Context

After ADR 0015-0017 the Metal code no longer read well:
- One 780-line kernels.metal in the order the kernels were written, with
  comments describing replaced versions ("staged 8 positions at a time").
- Kernel choice spread over `qr_run` and `encode_gemv` conditions.
- An unused decode kernel (`attention_split_par`, only for G != 4) and a
  generic one used only by the tiny fixture (`attention_split`).
- Two ad-hoc A/B switches (`--no-tensor-matmul`, `--no-tensor-attention`).
- Duplicated helpers in the tensor library.

Some paths (the level-1 kernels of RMSNorm and the DeltaNet rule, the
fallbacks) were never run by any test.

## Decision

- Every op has a **level-1 (reference)** kernel that mirrors the CPU code
  (one thread per output, group or head). Some ops add a **level-2
  (simdgroup)** kernel (SIMD groups, 8x8 simdgroup matrices; any Apple GPU)
  and a **level-3 (tensor)** kernel (Metal 4 tensor ops; optional library).
  The same level structure applies to every op.
- `native/metal/kernels/`, one file per op family:
  - Files: common, elementwise, norm, deltanet, attention_decode,
    attention_prefill, matmul, tensor.
  - Inside each file the order is level 1 -> 2 -> 3, with comments that
    describe the current kernels only.
  - `tools/build-metal.sh` concatenates them in reading order. The tensor
    library is common + tensor, so `Scalars` and the helpers exist once.
  - The thread macro `T` became `ITEM_ARGS`, because `T` collided with
    template parameters in the MetalPerformancePrimitives headers.
- `bridge.mm`:
  - The pipelines live in one `Kernels` struct grouped by op and level,
    loaded from a table.
  - One dispatcher per op family (`run_rms_norm`, `run_delta_rule`,
    `run_attention_decode`, `run_attention_prefill`, `run_matmul`). Each
    takes the highest level that is allowed, available, and supports the
    shape.
- Bridge option `kernel_level` (1..3, default 3), exposed as
  `DeviceModel::set_kernel_level` and `--metal-kernels
  reference|simdgroup|tensor`; reports record `"kernels"`. `device_info`
  has `kernel_level_max`. `matmul_relaxed` requires level 3.
- Removed: `attention_split` and `attention_split_par`. Shapes outside
  level 2 (G != 4 or head_dim not 64/128/256) use the level-1 three-pass
  decode read. `delta_rule_reg` was already gone.
- Test `device_real_kernel_levels` replaces `device_real_tensor_matmul`:
  - Real weights at each level: prefill in chunks of 7 and 128, then 4
    decode steps. Compared across levels with the FP32 tolerance and the
    same argmax at every step.
  - The tiny fixture checked at every level.
  - Relaxed GEMMs within their tolerance, plus a long check.

  Every kernel path now runs in a test.

## Consequences

M5, default settings, against a build of ADR 0017 (07462e7):
- Generated tokens and an exact hash of the prefill top-5 logits are
  identical on the 454-, 2644- and 10141-token prompts, also with
  `--matmul-relaxed`.
- Prefill and decode times are within run-to-run noise. For example, 2644
  tokens: 1.226-1.240 s vs 1.227-1.229 s; 10141 tokens: 5.33-5.38 s vs
  5.43-5.47 s.

Per level, 2644 tokens:

| level | prefill | decode |
|---|---|---|
| reference | 309 tok/s | 42.9 tok/s |
| simdgroup | 1,736 tok/s | 68.0 tok/s |
| tensor | 2,155 tok/s | 68.1 tok/s |

Generated tokens are the same at every level.
