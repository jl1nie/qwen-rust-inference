# ADR 0033: CUDA backend: the HIP bridge built with nvcc

Status: accepted; passed on GeForce RTX 4060 (sm_89), WSL2, CUDA 13.3. See
spec/cuda.md and spec/measurements/cuda-rtx4060.json.

## Context

Issue #46 measured one BF16 GEMV on CUDA (tools/bench_cuda_gemv). The
next step it named was a CUDA backend for the inference engine.

The engine side already allowed this. Rust owns weights, state and scratch
(`src/device.rs`). It loads a bridge library through a versioned C ABI and
checks its `qr_kind` (ADR 0004, 0005). The ROCm bridge (`native/rocm`) is
HIP C++. HIP is close to the CUDA runtime API, and gfx1100 runs wave32, so
its kernels already assume a 32-lane wave.

Three ways to get a CUDA bridge were possible:

1. A new bridge written for CUDA, as Metal has its own.
2. A copy of the HIP sources, converted (hipify).
3. The HIP sources compiled by nvcc, with the names mapped in a header.

(1) and (2) give a second copy of about 2,100 lines that every later
kernel change must repeat. This includes ADR 0019's fusions and ADR
0026/0029's snapshots, and their bitwise-equality arguments. (3) keeps one
source. The question is whether the HIP code is correct under CUDA's
rules, not only whether it compiles.

## Decision

**One source, two compilers.**

- `tools/build-cuda.sh` compiles `native/rocm/bridge.cpp` with nvcc, using
  `-x cu -DQR_CUDA -Inative/cuda`.
- `native/cuda/hip/hip_runtime.h` and `native/cuda/rocblas/rocblas.h`
  stand in for the HIP and rocBLAS headers. They map the names onto the
  CUDA runtime and cuBLAS.
  - `hipLaunchKernelGGL` is a function template over `cudaLaunchKernel`.
    A function rather than a `<<<>>>` macro, so that parenthesized
    template kernels compile.
  - cuBLAS (FP32 weights only, `--f32-weights`) is set to
    `CUBLAS_PEDANTIC_MATH`, so FP32 stays FP32 with no TF32.
- The build uses `--fmad=false` and `-ffp-contract=off`, like the HIP
  build: only the kernels' explicit `fmaf` fuse.
- The bridge returns `qr_kind` 3. Rust has `Kind::Cuda`, the `cuda`
  feature, and `cuda-check / -infer / -chat / -verify / -speculative`.
  These are the same engine and options as `rocm-*`.

**Warp semantics.** HIP's `__shfl_xor(v, o, 32)` takes no lane mask.
CUDA's `__shfl_xor_sync(mask, ...)` requires every lane in the mask to
reach the call. Since Volta, a warp's lanes also need not run in lockstep
(independent thread scheduling). Every shuffle in kernels.h was checked
against these rules:

- Row, head and query guards (`if (row >= rows) return`, `head_index()`,
  attention's `active`) are whole-warp. So the full mask is correct for
  `wave_sum`, `wave_max`, `block_sum`, `butterfly_sum`, argmax and the
  attention weight broadcast. The shim maps the unmasked HIP calls to
  full-mask CUDA ones.
- `delta_rule_column` is the exception. Its P-lane groups (one value
  column each) leave together when `column >= count`, so a warp can run
  the shuffles with some groups gone. With the tiny fixture this happens:
  `count * P` is not a multiple of 32.
  - The sums now go through `qr_shfl_xor_group<P>`. On CUDA it names the
    calling group's P lanes as the mask. On HIP it is the same unmasked
    shuffle as before.
- Shared-memory exchanges all sit behind `__syncthreads()`. None relies on
  lanes running in lockstep, so no `__syncwarp` was needed.

**Cross-block reads.** `gemv_bf16_add_norm` and `delta_mixer_split` read
other blocks' results in the last block (atomic ticket, then fence).
`load_agent` is `__hip_atomic_load(..., AGENT)` on HIP. On CUDA it is
`__ldcg`: a load from L2, which is coherent across SMs, skipping the
SM's L1, which is not.

**Not ported.** The opt-in 16-bit prefill attention (ADR 0014) uses
RDNA3's `v_wmma_f32_16x16x16_f16`. It is excluded under `QR_CUDA`, and the
CUDA bridge refuses `attention_f16` by name, as the CPU test bridge does.
A tensor-core version (`nvcuda::wmma`) would be a separate change.

The ROCm build is unchanged apart from the `#ifdef QR_CUDA` blocks. Its
HIP code is textually the same, except that DeltaRule's two shuffles now
go through an inline function returning the same `__shfl_xor`. It was not
rebuilt on an AMD GPU in this change (none on the CUDA machine). The CPU
test bridge, which builds `bridge.cpp` with `-Werror`, passes. A new CI job
compiles the CUDA bridge on every PR.

## Results (RTX 4060, WSL2, BF16)

Correctness (same commands and tolerances as ROCm, spec/rocm.md):

| check | CUDA | ROCm (RX 7900 XTX) |
|---|---|---|
| `device_gpu` tiny + 4 real-model tests | passed | passed |
| `--ids 16,10,16,28`, 1,364 records | 1.45e-4 | 1.52e-4 |
| long check 2,048 tokens | 1.54e-4 | 2.63e-4 |
| long check 8,192 tokens | 2.47e-4 (GPU prefill 5.9 s) | 1.04e-3 |
| chat: CPU and CUDA token IDs, save and resume across engines | identical | identical |

The 64 greedy tokens after `--ids 16,10,16,28`, and the text generated for
the 331-token prompt, equal the CPU engine's.

Speed: `cuda-infer`, chunk 128, 64 new tokens, medians of 3 runs. The
prompts and token counts are those of the ROCm records. The ROCm column is
ADR 0019's final state on a GPU with 3.5x the memory bandwidth (960 vs 272
GB/s).

| input | prefill CUDA | decode CUDA | decode ROCm |
|---|---|---|---|
| 4 tokens | 0.011 s | 130 token/s | 329 |
| 331 | 0.121 s | 130 | 330 |
| 1,267 | 0.444 s | 128 | 315 |
| 2,060 | 0.750 s (2,750 token/s) | 127 | 320 |
| 9,872 | 4.99 s (1,980 token/s) | 113 | 290 |

**Where a decode step goes.** With `QWEN_CUDA_PROFILE=host`, a token
takes 7.97 ms, 85% of it waiting for the GPU, over 130 bridge calls.
Reading the 1.5 GB of BF16 weights at the 246 GB/s that one GEMV reached
cold (issue #46) would take about 6.1 ms. 130 token/s is about 195 GB/s
of weights: 72% of the rating and 77% of the measured raw read rate.
ROCm reaches about 52% of its rating.

On WSL2 an ordinary launch costs about 9.5 us on the device timeline
(issue #46). If every call paid it, that would be about 1.2 ms of the 6.8
ms. This run did not separate the two. A per-call profile, or CUDA Graphs
for the decode step (0.75 us per node in issue #46, unlike HIP Graphs in
ADR 0019), would.

## Consequences

- One kernel source runs on AMD and NVIDIA. A kernel change must keep the
  shuffle rules above. Partial-warp shuffles need an explicit mask, and
  cross-block reads go through `load_agent`.
- `QWEN_CUDA_PROFILE` and `QWEN_CUDA_FIXED_GEMV` are the CUDA names of
  the ROCm profiler and A/B switches.
