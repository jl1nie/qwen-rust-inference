# ADR 0006: BF16 device weights and chunked device prefill

Status: experimental; passed on Apple M5 (macOS 27.3), Metal engine. ROCm
code paths compile only in CI and are not GPU-verified. See
spec/measurements/metal-m5-bf16.json. CPU reference remains the oracle and
ADR 0004 tolerances are unchanged.

## Context

After ADR 0005 the device engine was memory-bandwidth bound: every matrix was
uploaded as FP32 (about 3.0 GB for Qwen3.5-0.8B), every decode step read all
of it, and prefill ran one token at a time, re-reading all weights per token.

## Decision 1: BF16 matrices, only when lossless

The released checkpoint is BF16 and the loader widens it to f32 exactly, so
each f32 weight has its low 16 bits zero. `DeviceModel::load` stores a matrix
as BF16 (two values per 32-bit word, little-endian) only if EVERY value has
zero low bits (`WeightFormat::Bf16Exact`); otherwise that matrix stays FP32.
Kernels widen BF16 to f32 exactly (`bits << 16`) and accumulate in f32 in the
same order, so results equal the FP32-weight path; on Metal the GEMV is
bit-identical. Vectors (norm weights, gates, conv), activations, KV and
DeltaNet state stay FP32. `--f32-weights` keeps the old layout for A/B runs.
This is not quantization: no value changes, so no new tolerance is needed.
Lossy formats (FP16, int8/int4) would need their own ADR and tolerances.

## Decision 2: chunked prefill

`DeviceRun` allocates activation buffers for `chunk` rows (default
`PREFILL_CHUNK = 128`, `--prefill-chunk N`, 1 = token by token). One forward
pass handles up to `chunk` consecutive positions:
- projections are GEMMs Y[T,out] = X[T,in] W^T, reading each weight once per
  chunk; norms and elementwise ops run once over all rows;
- conv history and the DeltaNet rule loop the T tokens in time order inside
  each native thread, so recurrent state evolves exactly as in decode;
- Q/K norm + RoPE + KV append run per (token, head) with position p0+r;
- the attention read is still dispatched per token with its causal length
  (row r sees 0..=p0+r); this is the remaining long-context bottleneck
  (superseded by ADR 0007: one dispatch per chunk);
- only the last row goes through the final norm and vocabulary projection.

## ABI v2

`qr_abi() == 2`. Added `qr_gemv_bf16`, `qr_gemm`, `qr_gemm_bf16` and op
EmbedBf16 = 11 (widen one embedding row). New trailing `n` slots extend ops
to T tokens (ConvSilu n1/n2, DeltaQk n3, DeltaGates n0, DeltaRule n4/n5,
AttentionQuery n3); left 0 they mean one token, i.e. the v1 behavior.
BF16 buffers are allocated and written through the existing float-count
`qr_alloc`/`qr_write` as packed words, so no allocation API changed. v1
libraries are rejected.

Engines:
- CPU test bridge: plain loops; GEMM uses the GEMV loop order per token, so
  chunking and BF16 are bit-identical there (unit tests assert it).
- Metal: GEMV/GEMM for T < 8 share one SIMD-group-per-row kernel that reads a
  weight row once per 8 tokens with the GEMV summation order. For T >= 8 a
  tiled kernel (32x32 output tiles, `simdgroup_float8x8` multiply-accumulate,
  BF16 widened into threadgroup memory) is used; its blockwise summation
  order differs from GEMV, so chunked prefill matches decode within
  tolerance, not bitwise.
- ROCm: `rocblas_sgemm` for FP32 GEMM; BF16 uses a simple block-reduction
  kernel per (row, token). Not run on a GPU yet.

## Consequences

Measured on M5 (single runs): decode 28.8 -> 43.1 tok/s and prefill
39.7 -> 344 tok/s on a 2644-token prompt; 10k-token prompt prefill 306 s ->
88 s. Device matrix memory halves (3.0 -> 1.5 GB). The 2048-token long check
error is unchanged (3.2e-4). The CPU model still keeps FP32 weights in host
memory. Not done: batched/flash attention read, fused kernels, lossy
quantization.
