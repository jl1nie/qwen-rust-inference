# ADR 0012: keep checkpoint matrices as BF16 on the host, shared with Metal

Status: accepted; CPU and Metal verified on Apple M5 (macOS 27.3). CPU results
are bit-identical to the f32 copy; the model identity is unchanged, so
existing snapshots still load. See spec/measurements/host-bf16.json.

## Context

ADR 0002 widened every BF16 weight to f32 at load. The host then held about
3.0 GB of weights for 0.8B parameters, plus the 1.75 GB checkpoint file read
whole (peak RSS 4.9 GB). The GPU engines also kept this f32 copy next to
their BF16 device copy (peak 5.5 GB with Metal). Larger Qwen3.5 sizes would
not fit a 16 GB machine at all.

## Decision

- `Matrix` stores either f32 or the BF16 bit patterns in a page-aligned,
  whole-page allocation (`AlignedBuf`, 16 KiB pages). Kernels widen each
  element with `f32::from_bits(b << 16)`, which is exact, so every multiply
  sees the same f32 value as before. Sums keep their order:
  - Reference and Vector widen each weight where it is multiplied.
  - The sgemm path (`Optimized`) widens 64 rows at a time into a scratch
    buffer; output rows are independent dot products, so blocking the rows
    leaves every sum unchanged.
- Widening in a separate pass was measured and rejected for Vector (CPU
  decode, 4-token prompt): in-loop 16.4-16.6 token/s; 64-row scratch 10.8;
  L1-sized scratch (16 KiB) 11.4, also with a vectorizable widening loop.
  The CPU decode is compute-bound here: the extra store and re-read of the
  widened rows costs more than converting in registers.
  `row`/`values` return `Cow` (borrowed for f32, widened for BF16);
  `bf16_bits` exposes the bits.
- The loader reads the checkpoint in one sequential pass. Every byte goes
  through SHA-256, and each tensor is read straight into its final buffer:
  BF16 as bits, other dtypes decoded, ignored vision/MTP tensors hashed and
  dropped. Header checks follow the safetensors crate: contiguous offsets,
  sizes = shape x dtype, and the file ends where the data ends. Nothing is
  returned unless the whole file matches the pinned hash.
- BF16 vectors (norms, biases) are still widened to f32 (they are small).
  Fixtures and synthetic models still use f32 matrices.
- The model identity hashes BF16 tensors as their f32 widening, i.e. the same
  bytes as before, so identities and saved snapshots are unchanged.
- Metal: the device matrices ARE the host BF16 buffers. An optional bridge
  symbol `qr_wrap(ctx, &ptr, host, bytes)` creates an `MTLBuffer` over the
  host allocation with `newBufferWithBytesNoCopy` (no deallocator). The
  element layout matches the existing BF16 kernels (little-endian u16 = word
  2i in the low half), so kernels are unchanged. `DeviceMatrix` keeps an
  `Arc` of the host allocation, and its `Drop` waits for queued kernels before
  the memory can be freed. `qr_free` releases only the MTLBuffer.
- The symbol is optional, so the ABI stays v3. The HIP build does not export
  it (device memory is separate) and copies the bits (`upload_bf16_bits`).
  The CPU test bridge exports it so CI exercises the shared path. An f32
  matrix is still packed only when every value is exact.
- `bench` reports `weight_bytes` (as held in memory) instead of
  `weights_f32_bytes`.

Rejected:
- Converting to f32 per projection call: it allocates a full matrix per call.
- Widening into a scratch buffer for the Vector backend: 30% slower (above).
- Memory-mapping the file: it needs a new dependency or platform `mmap`, and
  it would still count file pages in RSS.

## Consequences

M5, BF16 checkpoint:
- Host weights: 3.01 GB -> 1.51 GB.
- Peak RSS of CPU `infer`: 4.9 GB -> 1.54 GB.
- Peak RSS of `metal-infer` (454-token prompt, 64 new tokens): 5.5 GB ->
  1.98 GB. Weights exist once for CPU and GPU.
- Weight upload: 1.58 s -> 0.03 s. Total run: 22 s -> 10 s.
- GPU speed and tokens unchanged: 454 tokens prefill 735-745 / decode 64.6
  token/s; 2644 tokens 727 / 60.9 token/s.
- CPU decode (Vector backend, 4-token prompt): 17.3 -> 16.4-16.6 token/s
  (-4 to -5%), the cost of widening in the loop.

CPU traces at a DeltaNet layer and an attention layer, through the logits,
are bit-identical to the previous build. Old snapshots load and continue
identically. A unit test checks BF16 vs f32 storage on all three backends
bit for bit; another checks the streaming reader. A CPU-bridge test runs a
BF16 matrix through `qr_wrap` and checks it bit for bit against the copied
upload (one token and a batch, odd sizes) and against the CPU projection. It
also checks that the device matrix keeps the host memory alive.

Addendum (after ADR 0013 parallelized the CPU projections; M5, same
commit, f32 storage rebuilt only for the comparison): with threads the CPU
decode becomes memory-bound and BF16 storage is clearly faster. Serial:
16.3 (BF16) vs 17.1 (f32) token/s. 2 threads: 27.6 vs 21.9. 4: 34.3 vs
21.9. 8 (default): 40.3 vs 27.2, i.e. 1.48x. On Metal, BF16 device weights
vs `--f32-weights`: decode 64.2 vs 37.3 token/s, prefill 744 vs 553, peak
RSS 2.0 vs 4.6-5.8 GB, same tokens (spec/measurements/cpu-parallel-m5.json).

Not done: BF16 KV, and zero-copy loading (the checkpoint file is still
read once into the buffers).
