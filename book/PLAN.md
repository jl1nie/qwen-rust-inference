# 執筆計画｜Rustで学ぶLLM推論

[執筆・検証・組版の実日計画](EXECUTION-PLAN.md)に、見開きごとの頁割り、作業日、確認版の条件を示す（章立ての変更に合わせて改訂予定）。

## この本で答える問い

Qwen3.5-0.8Bは、質問の文字列から「東京」というトークンをどう選ぶのか。その計算をRustでどう書き、GPUでどう速くするのか。

上巻では、CPU上で1トークン分の値と状態を追う。最後にFFNのパラメータを一列変え、どの計算が変わって次に出るトークンにどう影響するかを観測して、上巻を閉じる。この介入の着想は [Weight-Space Programming](https://rikiyat.github.io/blog/weight-space-programming/) の実験にある。

下巻は高速化に集中する。同じ計算をGPUに載せたとき、どのデータを何度読み、どこで同期するのか。速くした結果が、上巻のCPU版と合っているか。これを確かめる。

## 読者と説明の順序

読者は、Rustの配列・添字・ループを読めて、LLMが出力を選ぶ仕組みに興味のある人。機械学習、Transformer、線形代数、GPUカーネルは、初めて出る箇所で説明する。上巻の合成例は、実モデルのパラメータもGPUも要しない。下巻のGPU実測は、手元で実験する場合と、保存したログを読む場合の両方を案内する。

- **全体像を先に示す。** 第1章では細部に入らず、本書全体の地図を渡す。後の章はすべて、その地図のどこを詳しく見ているのかを冒頭で示す。
- **各節の順序。** 疑問 → 小さな具体例 → 数式とRustの対応 → 実モデルまたは実装での照合、を基本にする。概念を先にまとめて説明するのではなく、実際の値を追う途中で湧いた疑問に、その場で答える。
- **新しい用語。** 何を入力にして何を出力するかを先に示す。一つの節で導入する用語は少なくする。
- **省略と条件。** 模型で省く演算や、測定の条件を明記する。
- **読後の確認。** 読者が例の数値や入力の形を一つ変えたとき、結果を予想できるかを見る。

## 用語

本書のための造語や比喩の名詞は作らない。日本語の機械学習の文献で定着した訳語があれば、それを使う。なければ原文の英語を使う。

| 定着した訳語を使う | 英語のまま使う |
|---|---|
| 埋め込み、残差接続、正規化、全結合層、活性化関数、自己回帰、因果マスク、ヘッド、パラメータ | layer、position、hidden state、residual stream、token mixer、FFN、Q・K・V、attention weight、KV cache、state（DeltaNet）、LM head、logits、forward pass、prefill、decode、detokenize、logit lens、GEMM、GEMV |

- **パラメータと attention weight。** 学習で決まった値は「パラメータ」と呼び、attention weight と区別する。
- **decode の二つの意味。** トークナイザがIDを文字列へ戻す操作は detokenize と呼ぶ。HF tokenizers のメソッド名が `decode` であることは注記する。生成の decode とは区別する。
- **図には名前を付けない。** 本書の中心の図は「縦がlayer、横がposition」と説明する。

## 全体を貫く見方

本書の全体は、layer × position の図の上で説明する。

```
            position 0   1   2  …  19 │ 20   21 …
  LM head      ○        ○   ○       ◎  │ ◎    ◎
  layer 23     □        □   □       □  │ □    □
   …
  layer 0      □        □   □       □  │ □    □
  埋め込み      ●        ●   ●       ●  │ ●    ●
              ← プロンプト（最初から分かる）→│← 応答（1個ずつ決まる）→
```

- **二つのループ。** 外側のループは自己回帰生成で、右へ position を1つ足す。内側のループは forward pass で、1つの position を layer 0 から layer 23 まで下から上へ通す。
- **position は伸びる。** 最初から幅があるわけではない。応答のIDは、一つ左の列の頂上で選ばれてから足される。262,144（`max_position_embeddings`）は伸ばせる上限で、プロンプトと応答の合計で数える（`prefill_inner` が確かめる）。
- **パラメータは縦一列ぶん。** 各 layer のパラメータは、全 position で共有する。言語モデル部分は約7.5億個で、内訳は次のとおり。学習では全 position で同時に次のIDを採点して、この一組を決めたことを一言添える。
  - 埋め込み（LM head と共用）：2.54億
  - DeltaNet 18 layer：1.90億
  - Attention 6 layer：0.44億
  - FFN 24 layer：2.64億
- **1 layer の中。** 正規化 → token mixer → 残差接続 → 正規化 → FFN → 残差接続。
  - token mixer は、自分と左の position を読む。Attention（6 layer）か Gated DeltaNet（18 layer）が入る。
  - FFN は、自分の position だけで計算し、state を残さない。
- **Q・K・V は両方の token mixer にある。** 違いは過去の持ち方。
  - Attention は、KV cache に position ごとの k・v を並べる。position とともに伸び、1 position・1 layer あたり4 KiB。
  - DeltaNet は、固定サイズの state 行列に書き込む。1 layer あたり1 MiB。
- **prefill と decode は同じ関数。** どちらも `InferenceSession::ingest` → `Model::step_compact` で1列を計算する。
  - prefill は、プロンプトのIDを順に入れる。
  - decode は、一つ左の列の頂上で選んだIDを入れる。
  - prefill はIDが全部分かっているので、計算の順番を行ごとに入れ替えられる（GEMM）。decode は1列ずつしか進めない（GEMV）。この違いが下巻の出発点になる。

3.7節の冒頭に置く要約：

> prefillでは、全てのpositionのIDが最初から決まっている。そのため、一番下の行が最初から全部そろい、行方向（layerごと）にまとめて計算できる。decodeでは、次のIDは一つ左の列の頂上でlogitsが出るまで決まらない。そのため、1列ずつ縦方向にしか進めない。パラメータは行（layer）に付いていて、その行の全ての列で共有される。行でまとめれば、1つの行のパラメータを1回運ぶだけで、その行の全部の列に使える。

行の中でのまとめ方は、mixerの種類で違う。

- **FFN**：列ごとに独立しているので、そのまま一括で計算できる。
- **Attention**：一括で計算し、因果マスクで右の列を隠す。
- **DeltaNet**：stateを左から順に更新する依存が残るので、まとめ方に工夫が要る（第8章）。

forward passは「1列を下から上へ通すこと」で、prefillでもdecodeでも行う。縦にしか進めないのはdecodeだと、用語を取り違えないように書く。

続けて、次の問答を置く。数値はM5のMetal版の実測（`README.md`）で、1トークンあたりの時間に換算して示す。

1. **なぜprefillは速く、decodeは遅いのか。**
   - 1列の計算量は、prefillでもdecodeでも同じ（積和約7.5億回）。違うのは、パラメータ（BF16で約1.5 GB）をメモリから運ぶ回数。
   - prefillは約2,200 token/s（2,644トークンで1.2秒）で、1トークンあたり約0.45 ms。decodeは約74 token/sで、約13.5 ms。差は約30倍。
   - decodeでは、1.5 GB × 74 token/s ＝ 約110 GB/s。帯域の上限近くで、演算器はデータの到着を待っている（GEMV、メモリ律速）。
   - prefillでは、1回運んだパラメータを全部の列で使い回すので、演算器の速さで決まる（GEMM、演算律速）。
2. **新しいIDさえ決まれば、decodeもprefillと同じではないか。**
   - 1列の計算は同じ。実際、コードでも同じ `ingest` を通る。
   - ただし、パラメータを運ぶ時間（約13 ms）は「最初に一度だけ」ではなく、forward passを1回走らせるたびにかかる。GPUのキャッシュはパラメータ全体よりはるかに小さく、layer 23まで読むうちにlayer 0のパラメータは追い出されるからだ。
   - 1回のパスの時間は、運ぶ時間と、列の数に比例する計算時間の、大きい方で決まる。prefillは運ぶ時間を2,644列で割り勘にし、decodeは1列で丸ごと払う。
   - 次のIDは、そのパスの頂上で logits が出るまで決まらない。だから、同じパスに入れる列がない。
3. **では、次のIDを推測してまとめればよいのでは。**
   - その発想が、MTP（投機的decode、第10章）になる。
   - 次の数トークンを安く下書きし、1回のパスで小さなprefillのようにまとめて確かめる。当たった所まで採用し、外れた所から先のstateは巻き戻す。
   - 別々のユーザーのdecodeを1回のパスに並べるバッチ処理も、同じ割り勘の考え方だと一言添える。
   - 文脈が長いほど、decodeでは毎列KV cacheも読み直す。M5の記録では、約1万トークンの文脈でdecodeが約65 token/sに落ちる（第9章）。

## 下巻｜QwenをGPUで速くする

Apple Silicon（Metal）を主軸に、実装と測定の読み方をAMD（ROCm）とNVIDIA（CUDA）にも広げる。「Metal」は、AppleのGPU向けAPIと、実際に計算するGPUの二つを指す。章番号は上巻から引き継ぐ。

| 章 | 本文で追う順序 | 読者が確かめること |
|---|---|---|
| 7. CPUで正しさと速さの基準を作る | パラメータ、活性値、state の寿命を区別する → 手計算、固定fixture、上流実装との実パラメータ比較で、何が確かめられるか → 最初にずれた中間値を探す → FFNのgate射影（3,584行×1,024列）を1 positionと128 positionで使い、積和の回数とバイト数を数える → 帯域から速度の上限を見積もる → Rustが順番を決め、GPUが演算する役割分担 | 照合の三段階と、見積もりの前提を区別する。prefill（GEMM）と decode（GEMV）で、重みを読む回数がどう違うかを数える。 |

| 12. CUDAで同じ射影を組む | 同じ形のBF16 GEMV → warp内の部分和 → CPUで二重照合 → RTX 4060／WSL2でGraph・キャッシュ条件を変える → ROCmのカーネルをnvccでビルドした推論器 → CPU照合と速度 → 1ステップの内訳 | 前半は単体の射影の条件と、装置・発行方式・集計方法の違いを表で読む。後半は次を測定で示す：warpのマスクの違い、推論器全体の照合と速度、投機的decodeの倍率と少数行の検証の費用（M5・ROCmとの比較）、CUDA Graphを採らなかった理由、argmaxの2段化。 |

| 付録. コードと測定を再現する | 実装とモデルの版を固定し、3環境のコマンドと保存ログをたどる | 各章が根拠にした測定の条件とログを探せる。 |

下巻の巻き戻しの見開きでは、第5章の state の見開きと同じ記号を使う。

第9章の囲み記事「prompt cache の正体」：

- **何を保存するか。** 共通の先頭 N トークンを prefill し終えた時点の state を保存する。中身は、各 Attention layer の position 0〜N−1 の k・v と、DeltaNet 型 layer の state（と畳み込みの履歴）。パラメータ、途中の列の logits、hidden state は保存しない。次のリクエストでは、新しい部分の列だけを計算する。
- **なぜ先頭の完全一致が要るか。** 各列は、同じ行の左の全部の列に依存する。途中のトークンが1つ変われば、そこから右の k・v は全部変わる。
- **本リポジトリでの実例。** `metal-chat` の snapshot。2,637トークンの prefill 3.6秒が、読み込み0.24秒になる（`spec/measurements/metal-m5-chat.json`）。
- **メモリの量。** 1トークンあたり「layer 数 × KV ヘッド数 × ヘッドの次元 × 2 × バイト数」。比較表を置く：
  - Qwen3.5-0.8B は BF16 換算で 12 KiB。6 layer だけが伸びる KV cache を持つので小さく、3:1 の効果がここにも出る。本実装は f32 なので 24 KiB。
  - Llama 3.1 405B は約516 KB で、10万トークンなら約52 GB。
  - DeepSeek-V3 は MLA で圧縮し、約70 KB。
- **MLA（Multi-head Latent Attention）の一言説明。** DeepSeek-V2 で導入された。
  - 射影を2段に分ける。KV cache には、x を縮めた潜在ベクトル c（512個）と、RoPE 用の小さな k（64個、全ヘッドで共有）だけを置く。
  - k と v は、学習済みのパラメータ W_UK・W_UV で c から作る。ただし、q·(W_UK c) = (W_UKᵀ q)·c と掛け算の順番を入れ替えれば、k を作らずに済む。パラメータが固定だからこそできる。
  - RoPE は position ごとに回転が違い、この入れ替えを妨げる。そのため、RoPE 用の k だけを別に持つ。
  - 少し計算を増やす代わりに、帯域で律速される decode が読む量を減らす取引だと示す。
- **KV cache を小さくする方式の比較表。**

  | 方式 | KV cache に置くもの | 例 |
  |---|---|---|
  | MHA | 全ヘッドの k・v | 初期の Transformer |
  | GQA | 何個かのヘッドで k・v を共有する | Qwen3.5、Llama 3 |
  | MQA | 全ヘッドで k・v を1組だけ共有する | |
  | MLA | 圧縮した c と、RoPE 用の小さな k | DeepSeek-V2/V3、Kimi K2 |
  | 線形 Attention（DeltaNet など） | 固定サイズの state 行列（伸びない） | Qwen3.5 の18 layer |

  本書の Qwen は、GQA（KV cache を4分の1にする）と、3:1 の混ぜ方（伸びる KV cache を4分の1の layer に限る）の二つを組み合わせていると結ぶ。モデルの構成値は、執筆時に各モデルの config で確かめる。
- **商用APIとの関係。** 保持時間で書き込み料金が変わり、読み込みは prefill を飛ばせるので安い。この料金の形は、保存と再利用のコストを反映している。例として Claude の prompt caching（5分か1時間）を挙げる。ただし、内部構造や保存場所は公開されていないので推測しない。数字は執筆時の公式ドキュメントで確かめる。
